## 方案①：冻结协议迁移（已批准）

建议采用补强版 B，先把身份与兼容规则分清，再进行一个覆盖六包的迁移批次。源码重构不应迫使业务内容获得一个新的审核身份。

### 身份职责

| 身份 | 固定什么 | 何时改变 |
|---|---|---|
| 内容身份 | 明确枚举的业务文件原字节、材料/角色/业务规则及其版本 | 内容确实变化；逐文件差异必须另行审核 |
| 审核身份 | 审核者、审核范围、原报告/内容身份及日期；代码验收与内容审核分别记录 | 产生新的独立审核；禁止修改旧签署对象 |
| 评价逻辑版本 | rubric、规则语义、适用性、提示词与引用校验行为、受控对照基线 | 输出或判定语义改变；纯等价重构不升语义版本 |
| 代码身份 | 这次运行实际来自哪个提交/代码快照、是否含本地改动 | 任意实现改变；仅作为执行溯源及回退定位 |
| 发布/运行配置身份 | 内容身份、评价版本、协议版本与可运行的配置组合 | 安装组合改变；旧组合永久保留 |

反馈生成时追加代码提交号/快照来源、评价逻辑版本、规则和提示词版本、provider/model、`retries=0`，并保留确切作品版本、证据、权限和时间窗口。来源不能确认时明确标为未记录；不能给旧反馈补写一个猜测的提交号。历史反馈仍直接读取存储结果。

### 直接从仓库源码运行时的约束

评价版本是行为契约，不是另一份源文件哈希清单。内容包不保存“必须等于某个实现提交”的准入条件；评价版本表也不列出允许执行的源码 SHA。运行时按协议与评价版本兼容性装配，变更能否接受由独立审核和固定输入对照决定。

代码身份在进程启动时采集，反馈记录引用这次执行身份。正式验收使用干净的确切提交；若允许开发脏树运行，需给本次代码快照独立来源标识，不能写成干净提交已验证。进程运行期间变更源码必须重启，防止旧导入缓存与新磁盘代码混用。这里约束的是一次执行的来源一致性；源码重构后启动新进程即可，不要求给场景重绑。可保留源码摘要用于取证，但不能把它用于“与场景内预存实现摘要相等”的启动门槛。

阶段 A 的源码字节护栏只约束本次施工禁区。迁移获批后，源码部分应改用行为对照、协议兼容和独立审查，继续保护业务内容及旧发布原字节；不能把这份 2016 文件清单换一个名称长期挂在 CI 或启动器上，迫使每次等价重构重新重绑。

必须通过反例证明身份真的分离：只调整实现文件布局、行为对照相同，六包内容身份与原审核身份仍不变；改变评价输出则必须升级评价逻辑版本并提供新对照证据；修改业务文件则内容身份改变，旧审核不能继续覆盖。

### 正式迁移和六包切换

1. 用户批准后，固定当前六包和原源码/测试 ID 基线，先实现旧/新协议兼容读取及反馈来源字段。旧数据缺失新字段时标为未记录，保持原对象身份与结果。
2. 更新**现有正式 rebind CLI** 的协议能力与校验。当前 CLI 会改写 `scenario.yaml` revision，且只允许 rebind 工具本身的受控源码差异；它不能原封不动满足这次协议迁移。必须先把版本元数据移到生成的发布/运行描述，令内容文件逐文件不变，再由正式 CLI 出新包。禁止直接 patch 安装包、旧 manifest 或运行时自动修复。
3. 对主场景中文/英文和两个变体中文/英文，共六包，从当前发布目录导出到全新目标目录。内容文件清单及每个文件字节都与当前包比较；只允许事先列明的生成协议/发布描述变化，不用“语义相同”豁免内容差异。
4. 保留原审核对象和旧发布身份。新发布记录通过内容身份引用原审核，另附协议/代码验收；不把旧审核的 source hash 替换成新运行 hash。
5. 在候选新 catalog 上执行完整测试 ID 对比、A2 双语/MCP/恢复/历史回归、A3 固定反馈对照、原安装包读取回归。六包均通过后，以一次 catalog 指针切换作为上线候选；此动作仍须获得发布授权。
6. 回退保留旧 catalog、旧代码提交、原数据库备份和旧包。兼容读取先于写入新版本，不做破坏性数据库迁移；回退不得删除已产生的新版本反馈。若旧代码不能读新字段，则回退的是创建/执行路由，历史读取由兼容版本继续提供，不能把新记录静默降级。

默认选择**六包一批**，避免两个语言/变体处在不同冻结规则下。只有旧/新读写兼容必须分步建立时才采用两批：第一批六包建立兼容协议，第二批六包切换评价协议；两批各有完整对照与回退点。纯后端等价拆分不应再触发第二次内容审核或重绑。

闸门：只要无法证明业务内容逐文件不变、反馈语义等价、旧记录可读或事务安全不退化，就停在候选目录，不修改当前发布入口。

## 方案②：后端拆分（已批准，按顺序实施）

沿现有 `ExtensionRegistry` 和 `Operation` 注册扩展。模块继续产出 `Mutation`，由存储事务核心统一应用；不增加第二套命令分发、事务管理器或旁路写接口。

第一步只分离通用事务编排与对象规划代码。授权、幂等、乐观锁、引用解析和时间窗口、写入集合校验、对象/事件/快照/任务/请求结果落库保持在同一个数据库事务内。后续再逐类搬移业务规则，每次完整回归后才能继续。

私人作品只能通过分享授权对外可见、反馈及反馈响应不可改写、周期生命周期按既有会话／异步约束执行（2026-10-09接续决定撤回本次新增同步周期拒写），是事务核心的强制边界。它们不能变成模块可以选择不调用的辅助方法，也不能移到 HTTP 路由或提交前查询。直接命令、MCP、导入、后台 worker、重试/恢复等所有写入路径，都要经过同一组最终校验；尤其检验授权撤销、修订关闭与异步完成的竞争窗口。

建议为核心中的私有函数分别提供固定输入的事务上下文和待写对象集合；扩展 handler 只拿既有视图与请求，不获得直接提交数据库事务的能力。先迁移纯计划构造，再考虑持久化内部实现。v1 的创建和写入接口保持原协议，兼容读取不以删除 v1 实现为前提。

错误分类建议区分：输入格式/业务校验、认证/授权、版本冲突、依赖不可用、未知内部错误。公共响应使用稳定 code 与可行动的短说明；普通未分类 `ValueError` 不再一律映射为 422 并暴露内部异常文本。新增 logging 记录请求/会话关联标识、操作、结果类别、耗时、代码/评价版本；token、密钥、请求正文、私人作品与模型原文默认不写日志。意外异常保留受控服务端诊断，不把堆栈返给用户。

这部分会影响错误响应和运行契约，须在获准的后续批次中明确兼容性与预期行为变化，不能混入本轮前端等价重构。凭据派生问题、训练和预测模块、任意代码执行、部署均保持本次范围之外。
