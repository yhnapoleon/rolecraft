# 调研：模式识别的定位、可引入的训练场景与技术

日期：2026-10-16　基于：`origin/main` 319c2a9、[选型文档](pattern-recognition-selection-20261016.md)、[交接文档](handover-pattern-recognition-20261016.md)、v3 设计文档第 12–13 节、课程要求（`PRS-PatternRecognitionSystems-Practice-Module 7.0 - FT.pdf`）、第一次陈述稿 revision 8。

回答三个问题：当前情境下能引入哪些训练场景；能引入哪些模式识别技术；评审能不能一眼看出模式识别是这个系统的主体。方向已定（10-16 晚）：**不绕过 LLM，让识别器尽可能多地介入和覆盖，并成为 LLM 的主要决策依据输入源。**

## 0. 结论

1. **今天看不出来。** 产品里没有一个训练过的模型；评分由规则加 LLM Judge 决定；四个模型槽三个是 LLM；六个前端功能页没有一个是识别的。评审看到的是「带 AI 功能的培训工作台」。
2. **现有计划（C1–C6、C10、JUDGE）做完后能看出「有识别器」，看不出「识别器是主体」。** 识别器的输出是反馈卡里几行「模型建议（不计分）」和一张新页面。选型文档第 7 节自己承认了这个风险。
3. **要一眼看出，三件事缺一不可**：识别器占住每一个 LLM 调用的输入装配环节（第 3 节）；识别器在学员每一步都以「名字 + 分数」出场（第 5 节）；架构图和叙事以识别层为中心（第 5 节）。这三件事都是增补模块和改计划能做到的，不需要重做产品。
4. **新训练场景按改动成本分三档**（第 2 节）。本期只做零结构改动的档 A（换领域的事实根变体）和零成本的「执行者维度」（人 / 自带 Agent / 参考 Agent 同一任务），工程师路径作为第二个识别环节接 C1；需要改契约的档 C 不做。
5. **新识别技术只收「有界面时刻」的**（第 4 节）：仲裁器（Judge 与 C1 冲突识别）、意图识别 C11 提为必做、版本漂移的统计异常检测、提升图排队。其余课件方法留在报告作对照组。

## 1. 评审的参照系

课程文件对项目的要求只有一句话：「用 AI/ML 技术设计并构建一个模式识别系统解决真实问题」，至少覆盖四项（监督/无监督、ML/DL、混合集成、智能感知）中的三项。交付物第一条是「可运行的模式识别系统」，评分里最终系统占 15%、报告 15%、终期陈述 10%。

官方例子全是**单识别器系统**：皮肤癌检测、手势识别、缺陷检测、人群密度预测、食物识别三阶段。评审的默认心智模型是「一个系统 = 一个识别问题 + 一条流水线」。RoleCraft 是反过来的：一个大工作流里嵌了多个小识别器。所以「一眼看出」的难度不在技术，在于把多个小识别器组织成**一条**评审认得出的流水线。课件给了两条现成的：PSUPR 五段（采集→预处理→特征→分类/聚类→后处理）和 ISSM 流水线 B（原始数据→特征→实体→语义关系→上下文关系→知识）。

第一次陈述（10-05）已经对外说过的话，本期不能违背：主任务加两个变体；「工程师路径和案例面试模式是后续扩展」；识别任务是断言—证据关系判定；模型「只支持复核，目前不影响评分」；Judge 的 SFT/GRPO 是独立研究。新场景落在「工程师路径」「案例面试」两个名字里最安全；识别器「成为 Judge 的输入」与「不直接改分」不冲突。

## 2. 可引入的训练场景

### 2.1 平台今天能承载什么【已核实】

- 只有一个场景族 `pm_pilot`，结构 id `index_scope_resource_dependency`，三个变体（标准、urgent、capacity15）只改资源数字，中英各一份，共六个已安装包。
- **数据驱动的**：材料、事实、角色定义（可见材料、披露策略、审批权限、事件订阅）、助手领域到材料的映射、工作项代价、业务事件（触发 + 材料更新 + 通知）、探针、参考路径。
- **写死在代码里的**：产品类型（`AssistantConfig` 的字段：scope_filter、update_strategy、fallback、participants、launch_day）、工作项语义（`human_fallback`、`realtime_sync`、`scope_filter`）、动作集合（apply_config、refresh_index、request_business、read_material 等七个）、提交决定集合（launch / launch_narrow / defer_with_conditions / no_go）、14 项评分项与事实契约（假设 capacity、dev_days、deadline_day、政策变更）、评价事实生产器里的 `policy_travel` 和住宿报销匹配器、前端的工作项键与资源键。
- 场景编译器不生成场景，只校验作者声明并冻结已有包；没有「怎么写新场景」的指南。
- 工程师路径不是第二个场景，是同一会话上的第二个**角色**：拿 PM 的配置和失败记录，修配置、跑探针回归，五项顾问式评分项。
- 执行者维度已有：学员本人、学员自带 Agent（MCP）、参考 Agent，委托记录能区分。

### 2.2 三档候选

| 档 | 场景 | 改什么 | 天数 | 对识别器的价值 | 建议 |
|---|---|---|---|---|---|
| A | **换领域的事实根变体**：同一结构（索引滞后 × 范围 × 资源依赖），换成 IT 工单助手、入职问答助手、采购 FAQ 助手中的一到两个。材料、事实、角色、探针全用 `seed.py` 的生成机制重写内容，`policy_travel` 等写死处改成按事实名读取 | `scenarios/v2/content*.py` 新内容；`evaluation_facts.py` 三处写死的材料名参数化 | 每个领域 1.5 天（中英） | C1、C4 的**跨领域泛化测试**（在 pm_pilot 训、在新领域测，报告里最硬的一张表）；C5 轨迹多一个场景；C2 检索多一个语料。v3 第 3.2 节本来就计划了十个微场景账本只用于生数据，这一档把其中两个做成可玩的 | **做一个**，第二个看余量 |

| B2 | **案例面试模式**（陈述稿承诺过的扩展）：学员回答面试官三到五个问题，每答一题识别器判断「有依据 / 无依据 / 矛盾」，C11 判意图，C5 记轨迹 | 新角色 interviewer（roles.json 数据）、新回合类型复用 role_turn、评分项复用 R2.support 的规则界 | 2–3 天 | 识别器是这个模式的**全部**反馈来源，没有规则可以兜底，定位最清楚 | 有余量再做；没有就在报告写「已设计，接口复用」 |

### 2.3 场景不是重点

增加场景对「一眼看出模式识别」帮助有限：场景越多，工作流越大，识别器反而更被稀释。场景的价值在于给识别器提供**第二个分布**（跨领域泛化）和**第二个执行者**（人机判别）。所以档 A 做一个、A' 做满、B1 做，B2 看余量，到此为止。

## 3. 识别器成为 LLM 决策依据：三个入口【已核实接入点】

远端每个 LLM 调用前都有一个「输入装配」环节，识别器占住它就成了主要输入。

| LLM 入口 | 今天的输入装配 | 改为识别器装配 | 识别器 |
|---|---|---|---|
| JUDGE 评分 | `EvidencePackageV2`：断言、候选证据（整篇材料）、规则上下文（装配器结构化事实）、规则界；经 `model_input` 进 prompt | 候选证据 = C2 的 top-k 单元；规则上下文加「识别摘要」块（每句的关系标签与置信、C6 期望代价判定、数值与版本核查）；prompt 改为「先读识别结果再在规则界内裁定，引用识别器标出的句 id」；`AdvisoryJudge` 的 `support_check` 钩子换成 C1，对 LLM 引用的证据再核一遍 | C1、C2、C6 |
| ROLES 同事回合 | `roles_v2.py` 用词项重叠给角色选源 | C2 检索 + C11 意图识别决定角色看哪些源；C5 在线阶段写进角色上下文（「学员处于探索阶段，尚未读技术材料」）；回合后 C10 核查回复 | C2、C11、C5、C10 |
| ASSISTANT 知识助手 | BM25 top-1 → LLM 复述；`fallback = not hits` | C2 检索 + C4 范围判定 + 版本有效性检查决定给不给、给什么；LLM 只改写 | C2、C4 |

增补模块（相对选型文档）：N1 识别摘要装配器 1 天；N2 Judge prompt 改版与 `support_check` 替换 0.5 天；N3 角色选源换 C2 + C11，C11 提为必做 1 天；N4 C5 在线推断 0.5 天；N5 识别器 provenance 统一记录 0.5 天。合计 3.5 天，由砍 C7、C8、C9 报告版和 2 天余量支付。

报告里的对照实验：同一批提交，Judge「有识别摘要」与「无识别摘要」两种输入，比较标签一致性、引用命中率、待核验比例。这组数字证明识别器改变了 LLM 的决策，是「混合系统」最硬的证据。

## 5. 怎样做到「一眼看出」

把「一眼」操作化成三个可检查的标准：

1. **架构图 10 秒**：评审看架构图能说出至少三个识别器的名字。做法：架构图以识别层为中心画 ISSM 流水线 B，六个识别器是六个框，LLM 三个槽画成识别层外侧的「生成器」，工作台画成最外层。现在 `pre/revision8/RoleCraft_architecture.svg` 是以环境和 Agent 为双核心画的，要重画。
2. **任一页面一个分数**：打开任何一个学员页面，都能看到至少一个带模型名和数字的识别输出（第 4.2 节的界面时刻列）。做法：N5 的统一 provenance 对象，前端一个通用的「识别署名」组件渲染它，不逐页手写。
3. **视频前两分钟**：先放五个识别时刻（选型文档第 6 节），再讲业务场景。报告的系统设计章按 13.5 节的两条流水线写，第一节不是「RoleCraft 是什么」，是「这个系统识别什么」。

加一条**会话级汇总**：复盘页顶部一行「本次会话：范围检测 6 次、关系判定 24 句、意图识别 9 次、依据核查 9 条回复、轨迹识别 1 条、仲裁 2 项」。评审一句话就能数出识别器出场次数。
