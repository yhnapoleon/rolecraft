## 1. 目标与推进顺序

项目主要用于学校展示、简历中的可追问贡献和技术尝试。希望验证：Agent 能否根据当前工作问题提供合适的交互视图，让用户修改、选择和实际操作，再把结果用于后续判断。优先完成一条可复现的真实链路，不要求商业化配套或完整企业级平台。

界面生成的自由度可以从选择已有组件、动态组合组件，发展到生成 HTML/CSS/JavaScript。它们并非必须逐级升级的技术等级。用户操作是否能回到 Agent 的上下文，是另一条独立能力；首轮要明确哪些环节自动完成，哪些仍由用户手动传递。

| 顺序 | 探索内容与位置 | 需要证明的价值 | 当前状态与进入下一步的条件 |
|---|---|---|---|
| **第一阶段** | 事项中央作品区：Agent 生成的测试计划变成可编辑、可逐行运行的测试作品 | 从意图到作品、从用户操作到真实结果、从结果到证据的完整链路 | 已完成本机实现与验证，保留现有能力 |
| **第二阶段** | 反馈关联中央调查作品：根据问题组合分析、测试对照、来源核对与重测 | 减少寻找证据与切换工具的负担，同时保留用户判断 | 限定实现、自动验证与独立 IAB 的真实外部 Agent 闭环已完成；用户已确认本轮体验，尚无收益结论 |
| **第三阶段** | 自由作品中的临时交互画布：现场生成小工具或推演界面 | 探索生成界面代码的自由度、可理解性和展示效果 | 第二阶段试用后再定范围；先验证隔离运行和输入输出边界 |

各阶段结束时保留实际效果与失败例，不因排在计划中就自动推进。工作板、事项归属、资料入口和同事身份保持稳定；用户可以关闭生成视图，继续普通编辑、阅读和测试。现有模型、关系识别和评价实验继续按原计划推进，界面实验单独报告。

## 3. 第一阶段：可执行测试作品

### 3.1 用户体验

以“回应政策问答的开放请求”这一事项为首个展示情境。用户想验证某个试点承诺，向自己的 Agent 提供当前作品、选择的可见资料和已有测试。Agent 可以提出测试计划，也可以说明信息不足；不强迫每个请求都生成表格。

第一版已采用外部 Agent 任务包路径，工作流程如下：

1. **提出问题。** 用户说明想验证什么，并明确交给 Agent 的上下文。仅包含用户可读取且选择提供的资料，不提供隐藏答案、未来事件或其他角色私有信息。
2. **生成并预览。** Agent 返回普通文字或受支持的测试作品。测试作品展示问题、验证目的、可选的预期表现与依据。预览不能直接触发测试。
3. **采用与编辑。** 用户检查后采用到当前事项，也可修改、补充或删除测试行。旧 Markdown 作品继续正常使用。
4. **逐行运行。** 首个切片只要求显式运行单行。执行前固定该行及所属作品的修订、问题、预期和请求关联；未配置试点时提供现有设置入口。
5. **查看真实结果。** 回填助手回答、引用、运行条件与状态。用户可以重测、保留异议或补充观察。执行成功仅表示请求完成。
6. **纳入作品依据。** 用户选择具体运行作为证据。作品可导出可读摘要或并入既有交付稿；结果也可随下一次任务包交给 Agent 继续分析。

首个切片采用预定义测试表组件。只有 Agent 实际根据请求选择输出类型并生成内容，才记录为 Agent 驱动；固定样例 JSON 仅用来验证渲染和数据通路，不算模型效果证明。手动任务包路径不宣称实时双向连接。

### 3.2 最小作品与运行结构

下表描述本地作品与运行契约；实现字段见本轮工作区的作品引擎和 `types.ts`。这些本地字段不直接加入现有测试 API。首轮只允许普通文字和一种测试作品，不建设任意组件市场或通用页面生成器。

| 数据 | 建议保存的内容 | 作用与边界 |
|---|---|---|
| 回传信封 | 格式版本、任务包关联、独立的回传标识、输入快照引用 | 任务包标识与回传标识分开；相同任务包可有修正版，相同回传重复导入不创建重复作品；同回传标识内容不一致时提示冲突 |
| 测试作品 | 本地作品 ID、事项 ID、`kind`（如 `test_set`）、用途、来源、采用状态、作品 revision、可读摘要、测试行 | 当前本地用途使用“测试计划”等文字；后端接口需求中的 `plan` 是拟议映射，不擅自切换现有存档枚举 |
| 测试行 | 本地稳定行 ID、行 revision、问题、想验证什么、可选预期表现、可选材料引用 | 预期是待验证假设，不是标准答案；引用需核对实际可见 ID 与版本；本地身份由应用分配或校验映射 |
| 运行关联 | 会话、事项、作品/行及其 revision、执行时问题与预期快照、原请求 ID、执行状态 | 发请求前进入持久化日志。运行期间继续编辑不会改变已发请求或其结果归属 |
| 运行结果 | 真实 `testRunId` 及后端返回的回答、引用、配置/材料版本、时点 | 只由真实测试响应写入。Agent 回传的“已通过”、测试 ID、脚本和 API 地址不能变成运行事实 |
| 用户观察与证据 | 针对某次运行的判断、说明、引用关系 | 同一行可以有多次运行；引用变化纳入作品修订，保留引用的具体运行，不随最新结果漂移 |

回传校验失败时说明字段问题并保留原文，允许用户以普通文字保存；不要静默丢掉结构字段后声称导入了可执行作品。结构化预览和采用后的视图使用同一份已验证数据。正文摘要与结构化内容需有明确派生关系，避免表格已修改而交付摘要仍旧；保留正文出口是因为现有交付收集和任务包仍依赖 `body`。

v4 原导入按任务包 `requestId` 去重。第一阶段新增 `schemaVersion: 1`、独立 `returnId` 与 `artifact.kind: test_set`，旧回传继续兼容；相同回传内容去重，标识冲突拒绝。提供 `requestId` 时必须匹配已导出的任务包与事项，不提供时明确未关联。`saveArtifact` 和引用新增已记录完整测试行快照及作品修订。

首轮每份修正回传创建新的待检查候选，记录来源任务包、同包上一份回传标识（如有）及输入快照中的作品 revision；采用后仍是独立作品，不原地覆盖已采用作品，也不自动合并两个版本。目标事项不一致时拒绝导入；基底内容变化记录为待核对提示，不静默转移归属。生成输入快照包含当时选择的资料版本、配置/索引状态、已有运行 ID，以及实际交出的作品正文和草稿或已保存 revision。导入时比较当前记录与快照，采用前可查看已发现的变化。

### 3.3 执行契约与版本

现有 `POST /sessions/{id}/tests` 只接受 `query`、`config_version`、`request_id`。问题长度为 1–4,000 字符，空白问题会被拒绝；接口拒绝额外字段。测试目的、预期、作品/行 ID 和运行关联先保存在本地。测试同步完成，不经过角色对话的 worker 队列。

结果包含 `id`、`request_hash`、`query`、`answer`、`fallback`、`mode`、`citations`、`source_versions`、`indexed_versions`、`config_version`、`as_of_seq`、`stale`。展示时保留以下含义：

- `source_versions` 表示测试开始时的源材料版本；`indexed_versions` 在当前服务中记录本次检索采用的版本集合，最终引用可能只使用其中一部分，有效实时模式可直接使用源版本。
- `as_of_seq` 是测试保存前的状态序号，不能当成该请求结束后最新的世界序号。
- `stale` 表示实际引用存在过期版本，不自动等于答案错误；`fallback` 可能是预期的兜底表现。
- 返回值没有自动通过/失败评分、完整配置正文或服务端时间戳。前端保留的时间与配置副本要说明来源。
- 当前 API 创建的测试服务走 BM25 检索与本地抽取路径；角色对话接外部模型，不自动使知识助手测试也使用外部 LLM。生成测试作品的 Agent 与被测知识助手是两个独立环节。

**测试本身会推进场景。** `test_assistant` 增加业务动作计数，可能触发政策更新。因此每次运行展示其实际版本，不能给整张表统一套用“当前条件”。后续若加入“运行所选行”，应串行执行，遇失败、结果未确认或材料/配置条件变化时停下核对；批量执行不属于首个切片的必要范围。

**编辑后保留旧结果。** 行或验证意图变化后形成新修订，旧结果仍归属旧输入；界面提示当前行需要重测。相同问题可属于不同事项和意图，不能沿用仅按问题文字分组的方式作为行身份。重新测试追加运行记录，不覆盖历史。

### 3.4 恢复与失败处理

复用 Store 的原请求日志：网络断开、超时或 5xx 时保留未确认请求；恢复走 `execute`/`retry`，复用原 body 与请求 ID。重新调用 `store.test()` 会产生新 ID，属于新测试，不能用来恢复未知结果。4xx 为明确拒绝；409 后刷新状态，由用户核对后再发新请求，不静默改版本重发。相同请求 ID 携带不同测试内容，当前后端返回 422。

v4 原适配器仅在正常成功后补写事项归属。第一阶段已将关联保存到 `pending.localRun`，确认结果后保存到 `testRunMeta`；成功、重试成功及刷新恢复使用相同投影逻辑绑定结果。两份浏览器存档之间的投影可重复执行，以请求 ID 和真实测试 ID 去重；执行快照或 pending 关联持久化失败时停止发送，不允许只提示后继续执行。结果已在服务端完成但本地投影失败时，保留可恢复依据并明确状态，不能宣称已可靠保存。

首个切片允许“未运行、执行中、结果待确认、执行完成、执行失败”等运行状态。用户对是否符合预期另作判断。当前 `agentProgress` 中关联过测试就得到的 `verified` 标志，不可作为整份测试作品通过的依据。

## 4. 第一阶段验收与实现顺序

步骤 1–4 已完成；步骤 5 已验证一次真实 Codex 生成与回传，用户对照尚未执行。以下保留实现分解与验收要求。

| 顺序 | 交付内容 | 验证重点 |
|---|---|---|
| 1 | 明确第 7 节输入方式，确定一个展示请求与一份预期作品示例 | 能说清 Agent 决定了什么、用户决定了什么、哪些环节手动完成 |
| 2 | 版本化作品结构、旧存档兼容、导入校验、修订快照和可读摘要 | 合法/非法回传、旧 Markdown、不支持类型、重复回传、修正版、结构与摘要一致 |
| 3 | 事项内测试表及逐行编辑/运行；接既有 `LiveWorkbench` 与 Store | 用户修改影响实际请求；测试行和作品身份稳定；无配置与只读会话不能执行 |
| 4 | 发送前持久化归属、结果投影、原请求恢复、证据引用 | 超时后刷新重试仍回到正确行；重复点击不重复执行；运行中编辑不改变旧结果归属 |
| 5 | 使用真实 Agent 生成作品并走通一轮，再与普通文字计划比较 | 保留模型/输入/输出和用户修改证据；记录错误格式、错误引用、等待时间与实际操作价值 |

完成判据：

- Agent 生成的受支持测试作品能预览、采用、编辑、保存和恢复；其他普通作品仍可使用。
- 逐行运行调用真实测试接口，问题与用户确认的执行快照一致；返回值绑定具体行修订。
- 至少走通正常结果、兜底、材料版本变化、配置冲突、未知结果恢复和提交后只读的边界；不可用依赖如实列出。
- 修订后旧结果保留；相同问题的不同测试行不串联；引用来自真实材料/运行，不能通过回传伪造。
- 单次执行不自动获得“通过”结论；已采用、已运行、已关联证据和用户判断分别可见。
- 普通文字编辑、既有单题测试、Agent Markdown 回传、交付收集与 `/demo/` 的既有行为没有因共享引擎修改而破坏。
- 记录首个可用视图的等待时间、格式/引用问题、用户修正次数和完成操作的路径。若比较普通文字计划与测试作品，尽量保持问题、资料与帮助内容一致；没有用户实验就不声称提升学习效果或工作效率。

实现时在既有验证上补用例：[本地作品规则](../../apps/web/tests/workbench-state.cjs)、[Store 恢复](../../apps/web/src/store.test.ts)、[真实适配器](../../apps/web/src/workbench-live.test.ts)、[现有接口契约](../../apps/web/tests/test_existing_backend.py)、[后端版本测试](../../tests/integration/test_assistant_versions.py)。现有断线恢复用例不等于新的“测试作品行关联”已被验证。界面走查至少覆盖编辑、逐行执行、结果回填、重测、恢复、窄屏与键盘操作；中文/英文沿用现有界面约定。

首轮代码以 `apps/web` 的真实主入口、适配器、Store 和共享作品引擎为落点；单题后端契约可先保留。本轮实现仅修改前端及其验证文件，没有改变后端测试契约。以后若接内置生成 Agent，仍需单独定义生成入口与运行状态。

## 5. 第二阶段：情境化调查视图

**本轮限定实现及独立浏览器闭环已验证。** 首个情境围绕已有政策测试的回答、引用和源版本差异。用户可从规则反馈打开明确标注的起始调查，或把当前问题和实际记录交给外部 Agent；Agent 回传的模块选择与顺序按原样组成调查作品。规则起始视图是操作入口，不证明模型已经理解情境。

回传沿用 `schemaVersion: 1`、`returnId`、可选 `requestId`，新增 `artifact.kind: investigation`。作品包含标题、用途“探索笔记”、最多 1,000 字符的 `question` 和 1–8 个 `blocks`。模块可省略、重复组合和排序，不要求走固定顺序：

| 模块 | Agent 可提供的字段 | 工作台实际呈现与边界 |
|---|---|---|
| `note` | 可选标题（120 字符）、分析文字（2,000 字符） | 标明为 Agent 分析或规则整理，结论由用户核对 |
| `test_compare` | 1–4 个不重复的真实 `testIds` | 从实际运行读取问题、回答、引用和版本，不接受回传答案替代 |
| `source_check` | 真实 `testId` 与明确材料 `{id, version}` | 对比该次回答实际引用的版本与用户选择核对的版本；材料 ID 必须确实被该测试引用，两个版本可以不同 |
| `retest` | 真实 `testId`、可选标签（80 字符） | 用户采用并确认执行后，用该次测试的问题重新运行；保留原测试，追加新结果 |

应用分配模块 ID 和 revision；调整顺序只增加作品版本，修改模块内容增加对应模块版本。`question`、`blocks` 进入草稿、历史快照、存档恢复与导出输入快照，正文由结构派生。旧 Markdown、legacy JSON、`test_set` 继续兼容，另支持新版 `kind: text` 信封。外部回传不能注入模块身份、结果、脚本或原文。

**引用核验：** 提供任务包标识时，测试 ID 和目标材料版本须在该包的 `inputSnapshot.tests/materials` 中；测试还必须存在于当前会话实际记录，材料 ID 当前可读。无包回传仅能引用当前实际可见记录。历史目标版本只有在任务包明确包含时才能用于回传，包中版本标识本身不证明正文已经取得。

**来源读取：** `citationSource`、`materialVersion` 按会话、资料 ID、确切版本读取与缓存，优先实际可用内容，再查历史状态。找不到旧引用原文时显示缺失，不以当前版本冒充。导出历史材料正文仅使用已经成功取得的对应版本缓存。

**动作与恢复：** 重测复用现有测试 API，执行前独立保存 `investigationId/investigationRevision/blockId/blockRevision/baselineRunId`，不冒充第一阶段的测试行。返回结果归属原调查和模块，原请求恢复后仍能定位；暂停、已提交、未采用、已移除或版本不一致时不执行。模块选择与排序、分析和真实执行结果分别留存。

实现位于独立工作区的 `investigation-view.js`、`investigation.css`、`ui.js`、共享作品引擎、Store 与真实适配器。最终复跑 42 项 Vitest（含 4 项 HTTP）、67 项状态回归、构建与差异检查通过。

独立 IAB 测试会话从三模块规则起始调查导出实际任务包，当前 Codex 根据包选择 `source_check → note → test_compare → retest` 四模块，顺序与规则视图不同。回传预览、待检查时禁用重测/引用、采用、上下重排至 v3、实际重测及刷新恢复 v3/三条关联记录通过。来源核对分别展示 policy v1 的 500 与 policy v2 的 400 原文；未刷新索引的重测仍引用 v1。“关联测试”与“结论已验证”分开，界面没有自动判定后者。

图标编辑/预览/保存与键盘聚焦提示已验证；1440×1000 桌面及中英文 390×844 无横向溢出、控制台无错误。[实际任务包、Codex 回传与截图](../../apps/web/README.md#agent-ui-第二阶段情境化调查视图)保留本次合成验收证据。用户已确认本轮体验；没有用户对照试验，不声称改善效率或学习效果。

这一阶段没有实现完整情境化 Judge、内置生成模型、MCP 或任意界面代码执行。现有过程反馈仍保留规则来源；相关后端缺口继续沿[接口需求 P1-9](../design/frontend-interface-requirements.md#p1-9-过程反馈请求评审与不同看法)推进，且不与独立后端批次的已实现状态混写。用户可以关闭调查、继续原工作或提出异议。第三阶段保留为后续计划，不自动开始。

## 6. 第三阶段：临时交互工具

在“自由作品”中探索由 Agent 生成临时 HTML/CSS/JavaScript 工具。例如，基于已知资源与用户假设生成试点方案比较器，用户调整临时参数并保存选中的分析。

此阶段才引入生成代码的运行容器。先验证隔离方式、允许的输入输出、超时/错误展示以及产物保存；初始输入限于用户选择的只读场景快照和临时假设，禁止把应用凭据、存档或任意业务写入口直接交给生成页面。可以使用沙箱 iframe 等实现，但隔离效果需实际测试，不能仅因用了 iframe 就声称安全。

业务规则和正式测试结果来自可核对来源。自由生成的推演公式、假设和结果要可检查；推演结果不冒充后端测试或已批准配置。可以保存有版本的产物、输入与代码供回看，生成失败时仍能返回普通作品。

验收重点：临时工具能表达问题、操作有可理解的反馈、输入及假设可追溯、结果可保存、失败不影响原工作台。与受控组件路线比较生成等待、界面可用性、事实/计算错误和修改成本；选择一个工具展示即可，不提前建设通用应用生成平台。

## 7. 已确认的生成方式与下一步

2026-10-05 用户确认：先搭建好作品承接与执行能力，使用当前 Codex 等外部 Agent 实际生成并手动带回；内部 Agent 的自动连接以后再接。随后授权实现，并要求与整体设计和动效统一。这一确认取代此前“生成入口待选”的停点。

首轮已经落地逐行显式执行、预期由人核对、Markdown 兼容与真实结果留存。基础作品操作修复后，用户本轮明确要求紧凑图标与提示，并恢复第二阶段；这一要求取代此前暂停安排。第二阶段外部 Agent 浏览器闭环已在独立测试会话完成并留证。用户随后确认本轮体验，授权提交、推送、创建 PR，并在合并前验证通过后直接合并。内部自动连接、MCP 和第三阶段仍未实施；部署不在本轮范围。
