版本：2.0　日期：2026-10-06　配套规范：[扩建规范 v2.2](../specs/2026-10-06-rolecraft-expansion-spec.md)　数据计划：[数据收集与标注计划](2026-10-06-rolecraft-data-plan.md)

## 0. 怎么用这份计划

接手任何工作包之前，按这个顺序读：

1. 本文第 1、2、6、9 节：目标、执行模型、协作规则、起步步骤。
2. 规范第 1 节、第 3 节和第 15 节：评估结论、优先级、不变量。

## 1. 目标、交付物与完成标准

### 1.1 目标

到 2026-10-31，交付一个概念完整的演示系统：规范 1.2 节定义的图中场景可以由真人在浏览器里完成，也可以由学员自带的 Agent 通过 MCP 或 HTTP 完成；系统给出规则与语义结合的、可追溯的反馈；能从历史步骤分叉并比较；参考 Agent 的三种策略、技能记忆、自动优化、Jev 适配器和工程师路径各有一个可运行的最小实现；四类数据从真实运行中导出并由模型标注；课程要求的三类技术各有同集对照的实验结果。

### 1.2 什么叫“概念完整的演示”

演示必须能连续走完下面十段，每段都对应真实运行的产物，不用预先录好的假数据：

| 段 | 内容 | 产出证据 |
|---|---|---|
| 1 | 真人在工作台读材料、问角色、设计测试、比较方案、申请资源、应对政策更新、提交 | 会话时间线 |
| 2 | 学员把会话委托给自己的 Agent，Agent 通过 MCP 接手几步，再交还给人 | 轨迹里的执行者切换 |
| 3 | 提交后得到反馈：规则已定标、模型建议、待核验三组，每条引用可以点开 | 反馈页 |
| 4 | 过程诊断指出“忽略了可见的政策变更”，给出建议干预 | 诊断记录 |
| 5 | 从诊断建议的那一步分叉，换一个动作继续，比较两条路径的评分差异 | 分支比较 |
| 6 | 参考 Agent 用三种策略各跑一遍同一结构，对比成功率、关键事实召回、冗余动作 | E4 报告 |
| 7 | 从一批轨迹中整理出一条技能，在未见结构上比较有无技能的差异 | E5 最小报告 |
| 8 | 自动优化提出一个提示词候选，固定预算评测后与随机搜索对照 | E6 最小报告 |
| 9 | 工程师拿到任务包，修改助手配置，提交回归报告，平台复核 | 复核结果 |
| 10 | 数据集浏览：四类数据各一条，显示标签等级、来源和标注模型的校准结果 | 数据卡 |

每段都有一个可以独立运行的命令或页面；演示脚本见第 10 节。

## 2. 执行模型：并行 Agent 与波次

### 2.1 原则

1. **算力窗口前置。** 代码密集的工作（波次 0 到 2）集中在 GPT 订阅到期前完成；到期后剩下的是实验运行、集成、报告。具体日期见规范 U9。
2. **内核先行，契约冻结，再扇出。** 波次 0 修内核缺陷、定契约、拆路由；之后各泳道并行。契约在 WP-01 合入后冻结，再改只能走变更申请。
3. **一条泳道一个 Agent，一次只认领一个工作包。** 认领写进进度记录；完成或受阻时交接。
4. **下游先用夹具开发。** 等不到上游时，用脚本化模型、固定数据库夹具和已发布的契约先写代码和测试，上游合入后再联调。
5. **演示级验收。** 可运行、有运行记录、测试通过；不追求跨机器逐字节复现。
6. **人工只在关键路径上保留一处。** 同伴试用。其余人工事项（决策、密钥、算力）尽早给出，给不出就按默认值走。

### 2.2 波次

|---|---|---|---|
| 0 内核 | WP-00；WP-01；WP-04 的路由拆分步骤；数据计划 WP-D0、WP-D1 的分析部分 | 无 | WP-00、WP-01 合入；路由拆分合入 |

### 2.4 集成节奏

- 集成分支 `expansion`；每个工作包一个分支 `wp-NN-简短名称`。
- 每天至少合入一次：先在工作包分支上 rebase 到 `expansion`，全量测试通过后合入。
- L8 每天在合入后的 `expansion` 上跑一遍：全量测试、`career-lab demo`、`pm_pilot` v2 的四条路径测试、泄露测试。失败就在进度记录里点名，相关泳道先修。
- 推送、合并到 `main`、打标签需要用户授权。

**步骤**：

**验收**：技能文件通过契约校验；检索测试（前置条件过滤、预算限制、允许无技能）；整理命令从一批开发结构的轨迹产出至少 3 条去场景化候选（程序检查不含具体数值与材料名）；E5 最小对照在 2 个未见结构上完成；过期技能被失效条件拦下的测试通过；测试结构的轨迹未进入整理（用 lineage 核对）。

### WP-22 离线自动优化最小实现

**验收**：候选 diff 只触及搜索空间内对象的校验测试；一轮至少 3 个候选的运行记录（父候选、diff、假设、结果、成本）；与等预算随机搜索的对照；选中候选只对新运行生效的测试；评分规则与 gold 不在搜索空间的测试。

**开放点**：候选评测使用的结构数与预算。

### WP-23 工程师路径最小实现

**验收**：从一个 PM 会话生成任务包；提交一份修改后的配置与报告，复核重跑探针并与报告一致；规则评分四条可定标；回归报告可作为证据附到 PM 会话并被 R4 规则识别；补丁模式默认关闭。

**开放点**：规范 13.4 节的三项。

### WP-24 RuntimeBundle 与 EvaluationBundle 注册表

**目标**：让“固定版本运行”成为可检查的事实：每次参考 Agent 运行、每次反馈都引用一份带 hash 的执行配置和评价配置。

**规范依据**：v2.0 第 15 节；本规范 17 节。

**改动范围**：`src/career_lab/registry/bundles.py`；`bundles/runtime/*.yaml`、`bundles/evaluation/*.yaml`；`career-lab bundle freeze|verify|list`。

**验收**：RunManifest 与反馈记录都带 bundle 的 id 与 hash；修改 bundle 内任一引用文件后 `verify` 失败；优化选中的候选以新 bundle 发布，旧运行引用不变。

**开放点**：bundle 是否包含前端版本（默认不包含）。

### WP-90 冻结与确认性评测
