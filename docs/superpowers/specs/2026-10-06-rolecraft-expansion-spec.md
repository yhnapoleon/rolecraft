版本：2.2　日期：2026-10-06　文档类型：扩建规范（评估 + 范围 + 契约）

配套文档：[扩建执行计划](../plans/2026-10-06-rolecraft-expansion-plan.md)（波次、工作包、验收、协作规则）、[数据收集与标注计划](../plans/2026-10-06-rolecraft-data-plan.md)（数据来源、外部样例根因修复与溯源、模型标注流水线、发布）。本文只回答“现在的计划行不行”“要建成什么”“模块之间怎么对接”。

修订记录：v2.1 为同日早些时候的初稿，按“人工环节是瓶颈、范围收缩”作裁定。v2.2 依据用户同日的指示重排：交付物是概念完整的演示而不是可上线系统；每个模块做到可演示的最小实现，不要求稳定复现；数据标注由模型分批完成并二次确认，人工复核改为可选；工作由多个并行 Agent 在算力窗口内完成，不严格计算工作量。第 2 节的评估事实不变。

## 0. 文档定位

### 0.1 与 v2.0 目标架构的关系

[v2.0 目标架构](2026-10-04-rolecraft-target-architecture-design.md) 定义了最终能力和原则，但明确不安排阶段和优先级。本文在它的基础上做三件事：

1. 评估 v2.0 的合理性和可行性，并核对它能否实现“图中场景”（见 1.2 节的定义）。
2. 补上 v2.0 没有覆盖的三块：图中场景所需的场景内容与契约、学员自带 Agent 的接入、与工程师共用同一产品情境。
3. 给出优先级和裁剪线，并把优先级高的部分写成可以直接实现的契约。

发生冲突时按以下顺序取舍：

| 问题类型 | 以谁为准 |
|---|---|
| 范围、优先级、模块契约 | 本文 |
| 工作包顺序、验收、协作 | 执行计划 |
| 数据来源、标注方法、发布格式 | 数据计划 |
| 原则（状态权威、观察隔离、数据分区、版本固定、不把模型结果冒充人工结果） | v2.0 |
| 当前实现到什么程度 | 源码和测试 |

### 0.2 三种陈述的标记

本文区分三种陈述，接手的 Agent 应按标记决定信任程度：

- **【已核实】**：2026-10-06 当天通过运行命令或读取源码确认，表中给出核实方法。
- **【设计】**：本文提出的方案，尚未实现。
- **【估计】**：没有实测依据的判断，例如工作量和时间。

### 0.3 术语

| 术语 | 含义 |
|---|---|
| A / B | v2.0 的两条主线。A 是可执行环境与过程复盘；B 是 Agent 的主动信息获取（B1）、技能记忆（B2）、离线自动优化（B3） |
| G0 / G1 / G2 / G2v | 标签等级。G0 由程序核验；G1 由两位真人标注并裁决（本期不产出）；G2 是模型单次给出的标签；G2v 是模型两次独立标注一致、或不一致时经第三次裁决的标签，仍属模型标签 |
| 演示级 | 本期的验收标准：可运行、有运行记录、测试通过；不要求跨机器逐字节复现 |
| 结构（structure） | 一个场景的因果结构。只改数值或措辞的变体与原场景属于同一结构，必须留在同一数据分区 |
| 规则界 | 规则对一条评分项给出的下限和上限标签，语义模型只能在这个范围内判断（6.2 节） |
| 执行者（executor） | 实际操作的是谁：真人、学员自带的 Agent，还是系统的参考 Agent。与业务身份 `actor_id` 分开记录 |
| P0 / P1 / P2 | 优先级。P0 是演示主线，必须有；P1 是架构完整所需的最小实现，默认全部做；P2 有余力再做 |

## 1. 评估结论

### 1.1 四条结论

1. **v2.0 的方向合理，但作为扩建计划不完整：它没有优先级，也没有区分“生产级”和“概念演示级”。** 它的架构原则和现有代码一致，引用经得起核对。但它列出 11 项实验、14 类核心对象、5 个新子系统，却没有说先做什么；而提案承诺的截止日是 2026-10-31，提案里已经承诺的编码器微调、Judge 后训练、前端和真人试用都还没有开始。按生产级标准全量实施，截止日前做不到；按概念演示级标准（每个模块有可运行的最小实现、架构完整、想法得到验证、不要求稳定复现），由多个并行 Agent 实施，全覆盖是可行的，前提是先修好 2.1 节列出的内核缺陷，并把人工环节从关键路径上移开。

2. **图中场景在机制上已经能走通，但还不能真正用来训练。** 一次 27 步的真实运行已在现有后端完成，回放稳定。但同一次运行的系统反馈覆盖率是 0，知识助手对范围外问题直接返回整篇 FAQ，角色在本地模式下把私有事实原样告诉了学员。场景要成立，缺的是四样东西：可供调查的需求与失败材料、能测出差异的知识助手、能覆盖多数评分项的反馈、给人和给 Agent 的操作界面。这四样都属于 A，而 v2.0 把新增投入主要放在了 B。

3. **“使用自己的 Agent”和“与工程师共用同一产品情境”不在 v2.0 的覆盖范围内。** v2.0 的四种使用模式里没有学员自带 Agent；它把产品定位写成“面向 AI 产品经理”，工程师路径没有出现。提案把工程师路径列为核心完成后的扩展，也是范围收缩时第一个去掉的部分。

4. **数据草稿的切面设计是对的，但现有条目不能入库。** “一条轨迹的四个切面”这个思路成立。问题在于草稿是手工推演的：两份合成会话相互矛盾，都与引擎的真实行为不符；外部样例的字段与现有契约不兼容。正确的做法是让数据从真实运行中导出，草稿只作格式参考。

### 1.2 “图中场景”的定义

本文把用户提供的截图概括为下面这段话，后文都以它为验收对象：

> 主任务是决定内部知识助手能否开展试点，以及先服务谁、开放什么、如何保障、何时调整或暂停。任务包含需求调查、失败分析、自主设计测试、比较方案、资源协商、应对变更和提交决策七类工作；允许多种合理方案、自由组织事项、使用自己的 Agent。酒店报销上限只是其中一条测试素材。AI 产品经理和 AI 应用工程师共用同一产品情境：前者分析失败案例与用户需求、定义验收条件、决定试点范围；后者复现检索和回答问题、修改代码或配置、提交测试与回归结果。

### 1.3 建议

按 3 节的优先级和执行计划的波次实施：先修内核并冻结契约，再把图中场景做成可玩、可评、可导出数据的状态，然后同时铺开 v2.0 的全部模块，每个都做到可演示的最小实现。数据收集、标注和发布单独成一份计划：标注由模型分批完成并二次确认，人工复核改为可选抽检。交付物是一个概念完整的演示，不是可上线系统；报告如实写明哪些数字来自模型标注、哪些实验只做到冒烟。

### 2.3 v2.0 的合理性

站得住的部分：

- 状态权威在场景引擎，模型只提建议，由工具服务校验和提交。现有代码已经这样实现，角色对话不能批准资源。
- 观察与权威状态分开，“有权获得”和“已经获得”分开。
- 四种复现方式（事件回放、录制响应重放、再运行、干预分支）分开陈述。
- 标签分 G0、G1、G2；按场景结构分区；看过的测试集降级为回归集。
- 执行配置和评价配置分开，优化执行者时不能顺手改评分标准。
- 对自身边界诚实：明确说明不代表已实现，允许负结果。

需要修正的部分：

1. **没有优先级。** 文档写明不安排阶段。结果是 B 的三个模块、Jev、场景编译器、后训练和前端并列，无法判断先做什么、时间不够时砍什么。
2. **投入方向与场景的真实瓶颈错位。** 2.2 节的缺口几乎都在场景内容、契约和反馈上，属于 A；v2.0 的新增篇幅主要在 B。
3. **抽象层级高于代码现状。** 它描述通用的场景编译器、状态搜索和 CP-SAT；而现有契约写死了单一场景族（F8）。通用化是一次大改，对课程评分的贡献有限。
4. **B 的实验缺少前提。** 技能迁移、自动优化、结构泛化这几项实验需要多个因果结构不同的场景。按 v2.0 自己的规则，现有三个场景只算一个结构（F9）。
5. **把反馈当作“深化”，而它其实是最薄弱的环节。** 规则最多定标 12 项里的 2 项；语义 Judge 不存在；关系分类器在测试集上 Macro-F1 为 0.65、误扣分率 33%。
6. **没有承接提案的承诺。** 编码器微调、人工双标和同伴试用在 v2.0 里只是实验矩阵中的若干行，没有被标成必须交付。

### 2.4 可行性

约束条件：距截止日 25 天；4 名成员；本机无 GPU；人工标注尚未开始；小组有一个即将到期的 GPT Pro 订阅（含三张充值卡），可用于并行 Agent 开发和模型标注。

现有后端的大部分和全部受控实验是在 10 月 2 日到 3 日完成的（见 [实施进度](../../reports/implementation-progress.md)），而人工标注在这之后三天进度仍为 0。这说明写代码不是瓶颈，只能由人完成的环节才是。用户的指示据此是：标注改由模型完成，内容审查改为程序加模型检查，人工只保留决策、算力与密钥、试用和报告；工作由多个并行 Agent 在订阅到期前集中完成。

在这个前提下，v2.0 的每个模块都可以做到演示级。关键在顺序：先修内核缺陷并冻结契约，再铺开；否则并行的 Agent 会在有缺陷的内核上各自堆代码。

| 组成部分 | 演示级可行性【估计】 | 依据 | 处置 |
|---|---|---|---|
| 内核修复（反馈预算、披露、触发器、助手行为） | 高 | 缺陷已定位，改动范围小 | 波次 0 到 1，P0 |
| 场景内容、契约、助手模拟器 | 高 | 引擎骨架已在；材料可由模型按事实账本起草，再做程序和模型检查 | P0 |

### 2.5 数据草稿评估

`data/external-samples/` 下 12 个文件，分两类：两份合成会话，四份外部来源样例。

| 文件 | 可取之处 | 问题 |
|---|---|---|
| `showcase-one-flow-four-datasets` | 提出“一条轨迹，四个切面”；一主一支得到同一评分项上的正反样本 | 在现有引擎上不可执行：配置前测试、假设默认配置 c0、按“业务动作”计数触发政策（F19） |
| `synthetic-scenario-chain` | 纠正了触发时点；每步带状态和信念；字段最接近真实对象 | 手工推演，没有运行；测试的 `label` 和成果的 `name` 字段现在不存在；角色回复包含场景事实之外的内容（工单占比、用户组建议）；助手对范围外问题的回答与真实行为相反（F6）；系统反馈覆盖率写 0.2，实测为 0（F3） |
| `open-source-pm-samples`（关系，18 条） | 有真实的政策改版和审批阈值；许可和版本记录完整 | 每条 4 条候选证据，测试集是 8 条；译文未核对；标签由模型给出；`approval` 不在现有六个能力族里；字段不兼容（F18） |
| `judge-criterion-samples`（评价项，9 条） | 评分标准和判断都来自真实来源 | 没有 NOT_MET 和 INSUFFICIENT；标签映射规则是整理时自定的；TheAgentCompany 运行记录仓库没有声明许可，不能随数据集发布 |
| `process-trajectory-samples`（轨迹，4 条） | 三种来源展示了三类不同的过程错误 | Jira 变更历史的结构是字段变更而不是动作；tau-bench 那条不是 PM 场景；诊断标注由模型给出 |
| `info-action-synthetic-samples`（信息动作，12 个决策点） | 候选动作的结果类型划分得清楚 | 成本、风险和“有效推进”都是假设值，标签由假设算出，不是环境反馈 |

结论：

- 四类数据的划分与 v2.0 第 14.1 节一致，保留。
- 草稿的格式作为 10 节数据契约的输入；条目本身不入库。
- 合成会话由真实运行替代：`runs/synthetic-flow` 已经证明同一流程可以在后端执行，差的只是把导出做成正式命令。
- 外部样例进入单独的“公开辅助”桶，许可不明的条目不发布。
- 信息动作的标签改由环境推导（8.3 节），不再依赖假设的成本表。
- 每个文件校验失败的具体原因、修复方式和溯源要求，见数据计划第 4 节。

## 3. 范围裁定

### 3.1 优先级

优先级回答“必须有什么”，执行计划的波次回答“先做什么”。两者分开，因为很多 P1 模块可以和 P0 并行开发。

| 级别 | 含义 | 内容 | 对应章节 |
|---|---|---|---|
| P0 演示主线 | 没有它演示讲不通 | 内核修复；契约 v2；`pm_pilot` v2；知识助手模拟器；证据组装与规则 v3；语义 Judge（建议模式）；工作台四页；自带 Agent 接入；数据导出与模型标注；编码器微调与混合评价 | 4、5、6、7、10、11、12 |
| P1 架构完整 | v2.0 的每个模块都要有可演示的最小实现 | 参考 Agent 与三种策略；重放式分支；过程诊断；场景生成流水线与至少 6 个结构；Judge SFT；Jev 适配器；技能记忆；自动优化；工程师路径；RuntimeBundle 与 EvaluationBundle 注册表；工作台复盘页与研究视图；同伴试用 | 8、9、13、14、17 |
| P2 有余力再做 | 不影响演示与报告 | GRPO；工程师页面；语义重排检索；录制响应重放的完整实现 | 11、13 |
| 不做 | — | 通用场景编译器与 CP-SAT；图数据库；多智能体团队；行为 RL；组织级账号系统 | — |

原则：内核与契约先于一切；数据流水线与标注尽早开始，因为它们的产出是后面所有实验的输入；B 的模块代码可以提前写，实验等场景结构够多之后再跑。

### 3.2 演示级与生产级的区别

本期所有验收按演示级。两者的区别写清楚，避免接手者按错标准：

## 4. 目标场景：`pm_pilot` v2

【设计】新场景放在 `scenarios/pm_pilot/v2/`。v1 的目录受 hash 清单保护，不修改。

### 4.1 任务与合法结论

学员要给出一个决定，取四种之一：

| 结论 | 含义 | 在本结构中是否可接受 |
|---|---|---|
| `launch` | 按计划范围开放 | 是 |
| `launch_narrow` | 缩小范围先行 | 是 |
| `defer_with_conditions` | 申请资源并延期开放 | 是，须有批准记录 |

### 4.2 七类工作

阶段只是事后的归类，不是流程约束。引擎只校验动作的前置条件，学员可以按任何顺序做。

### 4.3 场景内容清单

所有材料都是为训练虚构的。每份材料对应事实账本中的若干条事实。事实账本由负责该场景的 Agent 编写；材料可以由模型按账本起草。审查改为两道程序化检查：数值与版本的正则核对（材料中出现的每个数字都必须对应到账本的某条事实，或被显式标为无关），以及一次独立上下文的模型审阅（逐句判断是否与账本一致、是否泄露私有事实）。人工审定改为可选抽查。审查结果写入场景目录的 `review.json`。

知识库材料（会被知识助手检索）：

| 材料 | 性质 | 用途 |

| `faq` | 稳定，扩到 8 到 10 条 | 正常问题测试 |
| `policy_travel` | 动态；v1 住宿上限 500 元，v2 改为 400 元 | 过期回答测试。这就是“酒店”素材 |
| `policy_meal` | 稳定 | 第二条政策素材，避免所有政策测试都落在酒店上 |
| `policy_leave` | 稳定 | 第三条政策素材 |
| `it_security` | 含一条禁止自动回答的条目 | 禁止项与范围测试 |
| `onboarding` | 稳定 | 新员工用户组的需求来源 |

| 材料 | 内容 | 支撑的工作 |
|---|---|---|

### 4.4 可接受路径

多解以约束集合定义，不以作者的某一条操作顺序定义。至少登记四条可行路径：

| 路径 | 要点 | 是否需要批准 |
|---|---|---|
| A | 只开稳定知识域；政策问题转人工；范围过滤加人工 fallback，共 2 人日；第 7 天上线 | 否 |
| B | 开放政策域并做实时同步；6 人日；延至第 10 天 | 需要资源批准 |
| C | 只开稳定知识域，但把人数扩到 30 以上、60 以内 | 需要扩容批准 |
| D | 开放政策域，但政策域命中即转人工核验 | 否 |

路径登记在 `scenarios/pm_pilot/v2/solutions.yaml`，属于研究端夹具，不进入任何学员或 Agent 可见的输出。路径测试会真正在引擎上执行每条路径，并断言规则评分项不出现 NOT_MET。

### 4.5 事件与触发

政策更新的教学意图是：学员已经形成初步判断之后，事实发生变化。因此触发条件改为“第 2 次业务动作之后”，业务动作指配置试点、保存成果、提交申请。阅读材料、角色对话和测试不计数。v1 的触发语义保持不变。

### 4.6 知识助手模拟器

【设计】模拟器必须让不同的配置产生可观察的差异，否则“自主设计测试”没有意义（F6）。它同时是 PM 与工程师共用的那个“产品”。

检索单位从整篇文档改为片段（按二级标题或段落切分）。工程层配置如下：

```yaml
AssistantConfig:
  schema_version: 1
  domains: [stable_faq, policy_travel]  # 开放回答的知识域
  scope_filter: true        # true 只检索开放域；false 检索全部已索引文档，范围外问题会被硬答
  freshness: index          # index 读索引版本；realtime 读源版本
  freshness_guard: none     # 源与索引版本不一致时：none 不处理 / warn 附警告 / fallback 转人工
  top_k: 3
  min_score: 0.0            # 最高分低于它，视为没有依据
  human_fallback: false     # true：没有依据或被守卫拦下时转人工；false：仍返回最高分片段
  manual_domains: []        # 命中这些域直接转人工
  generator: extractive     # extractive 返回片段原文；llm 由模型依据片段作答
```

PM 层的 `PilotPlan` 通过确定性映射得到 `AssistantConfig`：

| PilotPlan | AssistantConfig |
|---|---|
| `knowledge_domains` | `domains` |
| 工作项含 `scope_filter` | `scope_filter: true` |
| `fallback: human` 且工作项含 `human_fallback` | `human_fallback: true` |
| `update_strategy: realtime`，工作项含 `realtime_sync`，且获批资源足够 | `freshness: realtime`；否则退回 `index` |
| `update_strategy: manual_policy` | `manual_domains` 取全部动态域 |

沿用现有原则：不可行的配置也可以测试，但能力只有在资源到位时才生效。

每个场景附带一份探针库 `probes.yaml`：作者写好的测试问题，以及每个问题在各类配置下的预期行为（从某片段的某版本作答、转人工、附警告）。探针库属于研究端，用于回归测试和 G0 标签；学员自由提出的问题没有预设答案。场景作者必须校准 `min_score`，使探针库的全部预期在模拟器上成立，这一条由自动测试保证。

## 5. 契约变更

### 5.1 总原则

1. **v1 契约的序列化形状保持不变。** `EvidencePackage`、`GoldAnnotation`、`CandidateEvidence` 不加字段，因为数据集的 `input_hash` 由它们的序列化结果计算。新形状用新类，放在 `contracts/v2/` 下。
2. **其余契约只做带默认值的增量扩展。** 会话把完整的场景规格以 JSON 存在数据库里，每次提交都会重新解析，而契约禁止未知字段；新增必填字段会让旧会话无法加载。
3. **幂等哈希不得因新增可选字段而改变。** `Action` 增加可选的执行者字段后，计算 `request_hash` 时要排除空值，使旧形状的请求得到与升级前相同的哈希。
4. **新增存储用新表。** 没有迁移机制（F10），不要给已有的表加列。

### 5.2 场景规格

在 `ScenarioSpec` 上增加以下可选字段，旧场景缺省即保持原行为：

```yaml
schema_version: 2                 # 缺省为 1
baseline_pilot: {...}             # 会话创建时的初始配置，配置版本为 0；有了它，学员一开始就能测试
user_groups:                      # 先服务谁
  - {id: new_hires, name: 新入职员工, size: 18, needs: [onboarding, stable_faq]}
knowledge_base:                   # 知识域到材料的映射，替代服务里写死的映射
  - {domain: stable_faq, materials: [faq, onboarding], mutable: false}
  - {domain: policy_travel, materials: [policy_travel], mutable: true}
assistant: {min_score: 0.0, top_k: 3, chunking: heading}
approval_tiers:                   # 资源协商的可批准档位
  - {rule_id: resources_approved, grants: {dev_days: 6, deadline_day: 10}}
key_fact_ids: [capacity, dev_days, ...]   # 研究端：这一结构里对决策关键的事实
lineage: {root_scenario_id: pm_pilot, structure_id: capacity_staleness_resource, derivation_id: v2}
```

事件触发器增加一种：

```yaml
trigger: {kind: after_tool_count, tools: [update_pilot, save_artifact, request_capacity, request_resources], count: 2}
```

事实增加披露规则：

```yaml
facts:
  - id: tech_internal_risk
    visible_to: [tech_lead]
    disclosure: paraphrase_only     # open（缺省）/ paraphrase_only / never
    disclosure_text: 有一个旧组件的复用可靠性仍在内部评估，暂时不便展开。
```

校验器里“必须有 `realtime_sync` 工作项”这一条只对 `schema_version` 为 1 的场景保留。

### 5.3 试点配置

`PilotPlan` 增加可选字段 `target_groups`（用户组 id 列表）和 `decision`（4.1 节的四种结论）。规则检查：`participants` 不超过所选用户组的人数之和，也不超过有效容量。

### 5.4 成果

成果增加类型。接口的保存成果请求增加 `kind`，缺省为 `plan`。

```yaml
kind: plan            # 最终方案，对应简报的 13 项要素
schema_version: 2
target_users: 首批服务新入职员工与行政支持，共 30 人
business_goal: ...
fallback_conditions: ...
acceptance: {criteria: ..., test_refs: [<测试记录 id>]}
metrics:
  - {name: 有效解答率, definition: 每周人工抽检 50 条，回答正确且能定位依据的比例, target: 不低于 80%}
observation_window: 上线后 2 周
owner: ...
exit_conditions:
  - {condition: 任一周错误政策回答达到 3 条, action: 政策域全部转人工并暂停扩容}
claims:               # 可选：学员声明的关键判断及其依据
  - {text: 试点 30 人未超过获批上限, evidence_refs: [...]}
assumptions:          # 可选：尚未证实的假设及检验方法
  - {text: 实时同步上线后政策回答不再过期, verification: 上线首周每日复测政策探针}
rationale: ...
```

知识范围、试点人数、更新策略、工作项与成本这四项不在成果里重复填写，直接取提交时绑定的配置版本。这样“方案与配置一致”中属于结构化的部分由构造保证。

```yaml
kind: test_plan
cases:
  - {label: T1, category: normal, query: 如何申请会议室？, expected: 与 FAQ 一致, acceptance: 回答正确且版本一致}
# category 取 normal / out_of_scope / dynamic / prohibited / other
```

```yaml
kind: options
options:
  - {name: A, participants: 30, knowledge_domains: [stable_faq], update_strategy: manual_policy,
     fallback: human, work_items: [scope_filter, human_fallback], launch_day: 7,
     needs_approval: [], pros: ..., cons: ...}
  - {name: B, ...}
preferred: B
rationale: ...
```

方案对比里的每个方案都可以送进现有的可行性探针 [solutions.py](../../../src/career_lab/scenarios/solutions.py)，得到程序核验的可行性结论。旧的 6 字段成果继续可读可写，供 v1 场景使用。

### 5.5 测试记录

测试请求增加可选的 `label`、`category`、`expected`、`case_ref`（指向测试计划里的用例）。测试结果增加：

```yaml
retrieved: [{chunk_id: faq#2, material_id: faq, version: 1, score: 3.2}]
behavior: answered          # answered / answered_with_warning / fallback
assistant_config: {...}     # 这次测试实际生效的工程层配置
realtime_effective: false
```

### 5.6 角色披露

角色的提示词里只放可以向学员披露的内容：

- 学员本来就可见的事实：原样放入。
- `disclosure: paraphrase_only` 的事实：只放入 `disclosure_text`，不放原始描述和取值。
- `disclosure: never` 的事实：不放入。

这样泄露在构造上不可能发生，不依赖模型自觉。本地提取式模式按同样的规则过滤。角色回合的结果增加 `disclosed_fact_ids`，列出这次提示词里提供给角色的事实，供证据和数据导出使用。

### 5.7 申请与决定

申请动作的参数从只有一句理由扩展为：

```yaml
reason: 政策咨询量大、错误代价高
requested: {dev_days: 6, deadline_day: 10}     # 或 {capacity: 45}
work_items: [realtime_sync, human_fallback]
evidence_refs: [...]                           # 可选
```

主管的决定仍由确定性策略给出，但三种结果都要写成事件：

| 结果 | 条件 | 事件 |
|---|---|---|
| 批准 | 申请必要，且不超过场景允许的档位 | 现有的批准事件 |
| 拒绝 | 申请不必要，或超出全部档位 | `request_rejected`，带原因代码，并清除待审状态 |
| 还价 | 超出当前档位但存在更低的档位 | `request_countered`，带可批准的档位。列 P1 |

现在被拒时抛出错误且不留记录，待审状态永远不清除。这既影响协商体验，也丢掉了一类有价值的过程数据。

### 5.8 执行者

`Action` 和 `Event` 增加可选字段：

`actor_id` 仍然是业务身份，学员自带的 Agent 的 `actor_id` 仍是 `learner`，权限和可见性与学员完全相同。`executor` 只记录是谁在操作，用于轨迹、统计和报告。

### 5.9 观察

## 6. 评价与反馈

### 6.1 流水线

```text
固定提交快照
→ 构建规则上下文（只读状态和记录，不受文本预算限制）
→ 规则给出每条评分项的规则界
→ 按评分项的证据类型选择证据，组装证据包
→ 语义 Judge 在规则界以内判断，并给出引用
→ 引用校验：存在、版本、时点
→ 合并：规则已定标 / 模型建议 / 待核验
→ 过程诊断，关联到评分项
→ 保存不可变反馈
```

与现状相比有两处关键改动：

1. **规则不再受文本预算限制。** 现在的实现里，一旦供模型阅读的文本超预算，规则上下文也被清空（[assembler.py:70-71](../../../src/career_lab/evidence/assembler.py#L70-L71)），这是 F3 的原因。规则只读结构化状态，本来就不需要这些文本。
2. **证据按评分项选择。** 现在每条评分项的证据包都装入全部材料和全部测试记录。改为按 rubric 里每条评分项声明的 `evidence_types` 选取。

### 6.2 规则界

每条评分项由规则给出一个下限和一个上限标签：

- 下限等于上限时，规则已定标，不再调用模型。
- 否则语义 Judge 在范围内判断；它的输出若超出范围，按无效处理。

这是“规则确认的不满足不能被模型抵消”的具体形式。举例：只做了一类功能测试时，R4.functional_tests 的上限是 PARTIAL，无论模型怎么看方案文本都不能给 MET。

### 6.3 规则 v3

规则版本升为 `rules-v3`；`rules-v2` 生成的历史反馈保持可读，不重算。

| 评分项 | 规则能确定的部分 | 留给语义判断的部分 |
|---|---|---|
| R1.target | 目标用户或业务目标为空，或结论为 `no_go`：NOT_MET | 用户组与需求证据是否对应 |
| R1.metrics | 没有指标：NOT_MET；有指标但缺定义或目标：上限 PARTIAL | 定义和口径是否可观察 |
| R2.support | 无 | 关键判断是否有当时可获得的证据支持；可借助关系模型 |
| R2.unknowns | 配置所需资源超过有效值且无批准：NOT_MET | 文本是否把假设写成了事实 |
| R2.failure_analysis（新增） | 没有任何失败案例被引用或复现：上限 PARTIAL | 识别的失败模式是否成立 |
| R3.capacity | 完全确定（已有） | — |
| R3.resources | 完全确定（已有） | — |
| R4.functional_tests | 按测试类别和验收标准确定：两类都有且有验收标准为 MET，只有一类为 PARTIAL，没有为 NOT_MET | 测试类别由学员自报，抽样复核 |
| R4.staleness_test | 不适用的情形；更新后没有测试：NOT_MET；有测试且提交配置下最新的动态测试不过期：MET；仍然过期：PARTIAL | — |
| R5.impact | 没有变更事件：不适用 | 方案是否说明了受影响的范围 |
| R5.adjustment | 不适用的情形；受影响却没有任何配置变更、刷新或复测：NOT_MET；已调整且复测通过：MET | 只在文本里提出调整但未同步配置：PARTIAL |
| R6.consistency | 结构化部分由构造保证；文本里的数字与配置冲突：上限 PARTIAL | 文本层面的其他冲突 |
| R6.operations | 负责人、观察窗口、退出条件及动作齐全：下限 PARTIAL；全缺：NOT_MET | 安排是否可执行 |
| R6.alternatives（新增） | 没有方案对比成果：NOT_MET；只有一个方案：上限 PARTIAL；方案被可行性探针判为不可行却被选中：上限 PARTIAL | 取舍理由是否成立 |

新增的两条评分项使 rubric 升为第 2 版，共 14 条；维度权重不变。rubric 第 2 版由一名成员快速审阅后启用；来不及时由独立上下文的模型审阅并把结论写入 `review.json`，人工审阅补做。

验收目标：在路径 A、路径 B 和“忽略变更”分支这三条回归会话上，规则已定标的权重从现在的 20 分提高到不低于 45 分（满分 100）。这个数字是目标，实测后写入报告。

### 6.4 语义 Judge

产品路径使用现有的模型适配器调用 LLM 接口。每次只判断一条评分项。

- 输入：评分项的完整文本（达标、部分达标、不达标、证据不足的条件，可接受的替代方案，禁止的捷径）、被评价对象的相关段落、带中性编号的证据、规则界。
- 输出：标签、引用的证据编号、原因代码、简短解释。
- 输入中不含任何 gold，也不含证据的类型提示以外的评价元数据。

失败处理：输出无法解析、标签越界或引用无效时重试一次；仍失败则该项记为待核验，并记录失败类型。基础设施故障不转换成语义标签。

### 6.5 引用校验

模型给出的每条引用都要通过三项检查：编号在证据包里存在；引用的版本在提交时点有效，或评分项本来就要求对比新旧版本；观察时点不晚于提交时点。不通过的引用被移除；移除后没有任何有效引用的肯定性判断降为待核验。

### 6.6 反馈结构与采用门槛

反馈按三类分别给出覆盖率：规则已定标、模型建议、待核验。分数区间只由规则已定标的部分收紧；模型建议在界面上单独呈现并注明“待人工确认”。

语义 Judge 有三种模式：`shadow`（只记录不展示）、`advisory`（展示为建议，不计分）、`scoring`（计分）。默认 `advisory`。升为 `scoring` 需要满足沿用自受控实验 v2 的预注册门槛：Macro-F1 不低于 0.8、误扣分率不高于 0.1、标签与证据同时正确的比例不低于 0.6。本期门槛在 G2v 测试集上评估，报告须写明真值来自模型标注；人工语义验证作为可选项记录。达不到就保持 `advisory`，这本身是可以如实报告的结果。

### 6.7 过程诊断

【设计，P1】诊断由确定性检测器完成，只读事件和记录，因此标签是 G0。

| 问题类型 | 检测条件 |
|---|---|
| 忽略可见变更 | 变更事件对学员可见，受影响的知识域仍在开放，提交前既没有读新版本也没有在事件之后测试 |
| 沿用过期测试 | 方案引用的测试早于最近一次相关的配置变更或材料版本变更 |
| 未经批准的假设 | 提交的配置需要的资源或容量超过有效值，而申请未获批或未提出 |
| 测试缺口 | 开放的知识域或失败模式没有对应类别的测试 |
| 冗余动作 | 状态没有变化的情况下重复同一次读取或测试 |
| 重复失败调用 | 同一个无效动作连续出现达到阈值 |
| 过早提交 | 提交时存在规则可确定的不达标项，且有可用动作可以修正 |

每条诊断给出：问题类型、最早的相关步骤、支持它的记录、受影响的评分项、一个建议的干预（从哪一步分叉、把哪个动作换成什么）。多个问题可以并存。诊断不读取模型的思考过程，也不把模型的自述当作因果证据。

## 7. 外部 Agent 接入

【设计，P0】目标是让学员用自己的 Agent（Claude Code、Codex，或任何支持 MCP 或 HTTP 的 Agent）完成同一任务，并且系统能分清每一步是谁做的。原则沿用提案：平台只评价返回的成果和观察到的动作，不控制外部 Agent，不为它提供沙箱。

### 7.1 接入面

| 接口 | 用途 |
|---|---|
| `POST /sessions/{id}/delegations` | 学员用会话令牌为自己的 Agent 签发委托令牌：`{label, scope: read \| act, expires_in_seconds}`。令牌权限不超过学员本人 |
| `DELETE /sessions/{id}/delegations/{delegation_id}` | 吊销 |
| `GET /sessions/{id}/observation?since_seq=` | 5.9 节的观察对象；`since_seq` 是事件游标 |
| `GET /sessions/{id}/tools` | 学员可用动作的清单，每项含工具名、JSON Schema 参数、对应的 HTTP 方法与路径、是否为后台任务 |
| 现有的动作、测试、成果、提交、对话、反馈接口 | 不新增并行接口；委托令牌直接调用 |
| `career-lab mcp --session <id> --token <委托令牌>` | 以 stdio 方式启动 MCP 服务器，把工具清单映射为 MCP 工具；后台任务（角色对话、反馈）在服务器内部轮询到完成再返回 |

### 7.2 记录与隔离

- 持委托令牌的请求，事件与动作里的 `executor` 记为 `{kind: delegate_agent, label}`；`actor_id` 仍为 `learner`。执行者由服务端从令牌推出，不接受请求体自报。
- 委托令牌不能访问研究接口、路径夹具、探针预期、关键事实清单和任何 gold。观察接口的泄露测试对委托令牌同样执行。
- 只读范围的令牌调用动作接口返回 403，并记录一次 `permission_denied`；这类记录进入信息动作数据。
- 反馈与报告把纯人工会话、有委托 Agent 参与的会话、参考 Agent 会话分开统计，并给出各执行者的动作数。

### 7.3 参考客户端与演示

- `examples/byo_agent_minimal.py`：不带模型，只用观察接口和工具清单按固定清单完成路径 A，作为接入正确性的基线。
- 演示：用一个真实的编码 Agent 通过 MCP 完成一次任务，保存其对话记录（去除密钥）和导出的轨迹；轨迹里应能看到执行者的切换，例如人先读材料，Agent 接手测试与配置，人最终提交。

### 7.4 留给实现者补全的点

- 是否另外导出一份 OpenAI 函数调用格式的工具清单（建议提供，成本低）。
- 后台任务的等待方式：MCP 服务器内轮询（默认）还是 SSE。
- 委托令牌的默认有效期与速率限制的数值。

## 8. 参考 Agent 与信息动作

【设计，P1】对应 v2.0 的 B1。参考 Agent 走与学员相同的动作和权限，执行者记为 `reference_agent`。它有三个用途：对照实验、批量产出轨迹数据、作为自带 Agent 接入的参考客户端。

### 8.1 信念状态

```yaml
BeliefState:
  goal: ...
  known_facts: [{fact: capacity, value: 30, source: {kind: document, id: technical, version: 1, seq: 5}}]
  unknowns: [...]
  conflicts: [...]
  hypotheses: [...]
  current_plan_ref: ...
  budget: {steps_left: 20}
  revision: 7
```

信念状态只由已经观察到的信息更新，不能从权威状态补全未知项。

### 8.2 三种对照策略

| 策略 | 做法 |
|---|---|
| 固定清单 | 按预先写好的顺序读材料、测试、配置、提交 |
| 普通工具循环 | LLM 直接在工具清单上循环，没有显式的信念状态 |
| 主动获取 | 维护信念状态；每步列出合法候选动作，估计各自能解决哪个未知项和成本，再选择 |

三者使用相同的模型、相同的步数和 token 预算。指标：任务成功（规则无 NOT_MET 且到达已登记的可行终态）、关键事实召回、冗余动作比例、预算内成功率、政策变更后的适应。

### 8.3 由环境推导的信息动作标签

在每个决策点，对每个合法候选动作，在状态的副本上实际执行一次，由结果决定标签：

| 结果类型 | 判定 |
|---|---|
| 无效或无权限 | 引擎拒绝 |
| 解决关键未知项 | 新获得的事实与该结构的关键事实清单有交集 |
| 只解决非关键项 | 获得了新事实，但都不在关键事实清单里 |
| 冗余 | 没有新事实，状态也没有变化 |
| 有效推进 | 业务动作使状态落在某条已登记可行路径上 |
| 过早提交 | 此时提交会出现规则可确定的不达标项 |

“学员已获得的事实”由记录推出：读过的材料所承载的事实、角色回合的 `disclosed_fact_ids`、测试记录暴露的版本信息。读材料和业务动作的标签是 G0；角色对话的标签以“角色如实回答”为前提，实际回复由包含性检查复核，不通过的记为 G2。成本权重是策略配置，不参与标签。

### 8.4 批量运行

参考 Agent 运行器接受一份 suite 清单：结构列表 × 策略 × 种子 × 预算，加故障注入选项（模型超时、工具错误、材料缺失）。每次运行写出 RunManifest、轨迹和决策点记录，供数据计划批量导出。suite 清单与运行记录就是 E4、E5、E6、E10 的输入；数据计划第 3 节给出产量目标。

## 9. 分支

### 9.1 重放式分叉

【设计，P1】分支是一个新会话：用同一份场景规格创建，然后按父会话的事件记录，把分叉点之前的动作连同已保存的对象（角色回复、测试记录、成果）原样重新提交一遍。对象 id 包含会话 id，所以重放时重新生成，并保存新旧 id 的对照表。

选择这个方案的理由：

- 不修改已有的表，只新增一张 `branches` 表记录父会话、分叉序号、干预和 id 对照表。
- 隔离是完全的：分支有自己的事件序列、幂等键和对象，父会话不被读写。
- 可以直接验证：分叉完成后，分支在分叉点的状态与父会话的对应快照在去掉会话 id 和对象 id 之后应当相同。

放弃的方案是“读穿透”，即分支在读取时回退到祖先的记录。它节省存储，但每个读路径都要处理祖先链，出错面大。

重放不重新调用模型，角色回复和助手回答都取自记录。分叉之后的延续可以是真人、参考 Agent 或脚本，延续方式写入分支记录。

### 9.2 分支比较

对父会话和分支分别生成反馈，逐项对比标签，并明确写出三件事：只改了什么、后续由谁执行、是否重新调用了模型。结果的表述是“模拟环境内的干预效果”。

诊断给出的建议干预可以自动执行为一次分叉，用来检验建议是否真的让受影响的评分项改变。

## 10. 数据规范

数据的来源、产量目标、外部样例的根因修复与溯源、模型标注流水线、分区与发布，全部在 [数据收集与标注计划](../plans/2026-10-06-rolecraft-data-plan.md) 中规定。本节只保留其他章节需要引用的定义。

### 10.1 四类数据

| 类型 | 一条记录 | 主要来源 | 标签 |
|---|---|---|---|
| 关系与证据 | 一句可核对的话，加带版本和时点的候选证据 | 助手回答、成果里的 `claims`、角色陈述、外部政策文本 | 数值、版本、记录是否存在类为 G0；其余为 G2v |
| 原子评价项 | 一条评分项、一份提交、证据 | 每次提交乘以 14 条评分项 | 规则已定标的为 G0；其余为 G2v |
| 过程轨迹 | 一次会话或分支的步骤序列，加诊断标注 | 真人、委托 Agent、参考 Agent、故障注入、分支 | 诊断检测器给出 G0；叙述性标注为 G2v |
| 信息动作 | 一个决策点及其候选动作 | 参考 Agent 运行 | 由环境推导（8.3 节），G0；角色对话类为 G2 |

四类数据来自同一次运行的不同切面，由一条导出命令生成：`career-lab export --database-url <数据库> --session <会话 id> --output <目录>`。

### 10.2 标签等级

| 等级 | 定义 | 本期是否产出 |
|---|---|---|
| G0 | 程序按数值、版本或记录存在性核验 | 是 |
| G1 | 两位真人独立标注并裁决 | 否。人工抽检（可选）只用于报告标注模型的可靠性，不把条目升级为 G1 |
| G2 | 模型单次标注 | 是，作为中间状态 |
| G2v | 模型两次独立标注（不同提示词版本、打乱证据顺序）一致；不一致时经第三次裁决并记录分歧 | 是，作为本期的语义真值 |

规则：G2v 不是 G1。任何报告、数据卡和界面都不得把模型标签表述为人工标签。标注模型在 G0 子集上的准确率随数据集一起发布，作为 G2v 可靠性的度量。

### 10.3 公共字段

每条记录都带 `schema_version`、`record_id`、`label_tier`、`bucket`（`env_run` / `human_session` / `public_aux` / `business_synth`）、`lineage`（结构、派生、会话、分支）、`split`（由结构决定）、`provenance`（导出命令、代码提交号、执行者；外部来源另带 `source` 与 `transformations`）、`language`。完整字段见数据计划第 8 节。

### 10.4 分区

按结构分区；同一结构的变体、改写、分支及其导出记录同分区。现有三个场景是同一结构，全部归训练集。受控实验 v2 的测试集只作回归。确认性评测使用从未参与选型、也从未用于调整标注提示词的新结构。测试分区的轨迹和反馈不进入技能库、优化器和标注提示词的调整。

## 11. 模型与实验

### 11.1 课程四个方向的对应

| 方向 | 本期交付 |
|---|---|
| 监督学习 | 关系三分类；评价项五分类；证据选择（每条候选证据是否应被引用） |
| 机器学习与深度学习 | TF-IDF 加逻辑回归；字符 MLP（按真实结构如实命名）；微调的多语言预训练编码器；小型生成式 Judge 的 SFT |
| 混合与集成 | 规则界加语义 Judge 的级联；线性模型与编码器的概率融合；逐项消融 |
| 意义建构 | 带版本和时点的证据有效性判断；过程诊断 |

### 11.2 编码器与证据选择

受控实验 v2 的核心问题是学习模型引用全部候选证据，使标签与证据同时正确的比例为 0。本期的编码器实验必须同时输出标签和证据选择。两个候选结构，在开发集上选型：

- 整包编码：把断言和全部候选证据拼接后输入，一个分类头给出三分类标签，另一个多标签头给出每条证据是否被引用。
- 逐条编码：对断言与每条证据分别判断支持、矛盾或无关，再由确定性规则聚合出标签和引用集合。

底座在 `xlm-roberta-base`（提案承诺）和一个中文预训练编码器之间按开发集结果选择，记录检查点、分词器和训练配置。训练环境独立于产品环境，依赖单独锁定。没有 GPU 时，用参数量更小的中文编码器在 CPU 上训练几百条，作为演示级结果，并在报告中标明规模。

## 13. 工程师路径

【设计，P1 最小实现】共享的产品情境由三样东西组成：同一份场景包（知识库、失败案例、探针库）、4.6 节的知识助手模拟器、同一批测试记录。工程师的任务是让助手在失败案例上表现正确，并提交可复核的回归结果。

### 13.1 对象

| 对象 | 内容 |
|---|---|
| 任务包 | 由 `career-lab engineer pack --session <PM 会话> --output <目录>` 生成：失败案例（场景的 `failure_cases` 加 PM 会话中失败或过期的测试记录）、当前生效的 `AssistantConfig`、探针库中标为 `public: true` 的部分、回归命令、提交模板 |
| 提交物 | 修改后的 `AssistantConfig`，可选地附一个只允许触及 `assistant/` 下白名单文件的补丁；一份 `regression_report.json`；一段修改说明 |
| 复核 | `career-lab engineer review --pack <目录> --submission <目录>`：用提交的配置重新运行全部探针（含非公开探针），比对提交的报告。规则评分：目标失败是否修复、是否引入新失败、总体通过率、报告是否与复跑一致 |
| 工程师 rubric | 五条：目标失败已修复；无回归；修改说明与配置差异一致；报告可复现；对未修复项有说明。前四条规则可定标，第五条由语义 Judge 建议 |

### 13.2 与 PM 路径的连接

- PM 的测试计划用例可以转为探针候选（`career-lab engineer probes-from-plan`）。
- 工程师的回归报告可以作为证据对象（`kind: regression_report`）附到 PM 会话，供 PM 在 `claims` 里引用；R4 的规则在有回归报告时把它视作实际测试记录的补充。
- 两条路径的会话互相引用：工程师会话记录 `parent_session_id`；PM 会话的观察里出现回归报告的目录。

### 13.3 边界

- 默认只运行自己的模拟器与探针库，不执行任意生成的软件环境。补丁模式只在容器内运行，且只允许改动白名单文件；本期可以只实现配置模式，补丁模式留开关。
- 工程师路径没有独立前端（P2）；演示用命令行与导出的报告。

### 13.4 留给实现者补全的点

- 工程师 rubric 的措辞和权重。
- 公开探针的比例（建议三分之一）。
- 是否把工程师会话也接入执行者记录与自带 Agent（建议接入，复用 7 节的机制）。

## 14. Jev、技能记忆与自动优化

### 14.1 Jev

【设计，P1，限时】新增独立的决策接口，与生成式的模型适配器并列：

```text
DecisionAdapter.decide(DecisionRequest) -> DecisionResult
```

请求与结果的字段沿用 v2.0 第 9.2 节。提供三个实现：调用 Jev 的实现、用 LLM 的结构化输出模拟同样问题类型的实现、本地分类器实现。实验报告必须注明每个结果实际来自哪个实现。

接入门槛：在约定日期前拿到密钥，并在 30 条中文关系样例上完成冒烟测试。达不到门槛时保留适配器和冒烟结果，对照实验改用 LLM 实现。首个用途是证据关系判断，对应 E3；动作排序、技能适用性和复核路由在门槛通过之后再考虑。

注意事项：请求里使用明确的版本号而不是 `jev-latest`，并记录响应中实际的模型版本；Noul 没有独立的置信度，Choice 和 Score 的置信度是概率分布的摘要，都不能直接当作正确率；密钥文件不入库、不进日志。

### 14.2 技能记忆

【设计，P1 最小实现】

- 存储：`skills/<技能 id>/v<版本>.yaml`，结构沿用 v2.0 第 10.1 节，另加 `applicable_structures`、`counterexamples`、`status`、`content_hash`。技能包是一份带 hash 的成员清单 `skill_bundles/<名称>.yaml`。
- 检索：先按状态、工具版本和前置条件过滤，再按目标与未知项做 BM25 召回；可选用 DecisionAdapter 判定适用性；装入数量受 token 预算限制；允许“没有适用技能”。
- 整理：`career-lab skills distill --trajectories <目录>`，从被授权的成功与失败轨迹中由 LLM 提出候选技能。候选必须去场景化（不含具体数值与材料名），由程序检查后进入 `candidate` 状态；在开发结构上验证后升为 `validated`。
- 一次运行固定一个技能包；测试结构的轨迹不进入整理。
- 实验 E5 的最小形式：无技能、手写技能、整理技能，在 2 个未见结构上比较成功率与成本；再用一个故意过期的技能检验失效条件是否拦截。

### 14.3 自动优化

【设计，P1 最小实现】

- 搜索空间清单 `optimization/search_space.yaml` 列出允许改动的对象：Agent 提示词、Judge 提示词、信息获取策略的权重与停止参数、检索 top-k。评分规则、gold、分区、角色授权不在其中；程序校验候选的 diff 只触及清单内对象。
- 候选循环：读取开发结构上的失败轨迹与反馈 → LLM 提出具名修改与假设 → 生成不可变 `CandidateBundle` → 固定预算运行 → 比较成功率、证据质量、成本 → 保留非支配候选。
- 对照：等预算随机搜索；1 到 2 轮即可。
- 产出：每个候选的父候选、diff、假设、运行记录、成本和选择理由；选中的候选只对新运行生效。
- GEPA 作为可选的优化器适配器接口保留，不作为依赖。

## 15. 不变量

以下各条任何工作包都不得破坏。执行计划第 6 节给出了对应的检查方法。

1. 全量测试保持通过。
2. v1 的场景目录、已发布的数据集目录和已冻结的研究目录不修改；变更一律发布为新版本、新目录。
3. v1 契约的序列化形状和哈希保持不变（5.1 节）。
4. 模型不直接改变权威状态；所有写入经过 reducer，并带期望版本和幂等键。
5. 学员和 Agent 可见的输出里不出现 gold、路径夹具、探针预期、关键事实清单、未来事件和不可披露的私有事实。
6. 规则评价不受模型输入预算的影响。
7. 反馈必须分别给出规则已定标、模型建议和待核验三类覆盖率；模型建议在通过门槛之前不计分。
8. 测试分区不参与训练、调参、提示词选择和技能整理；看过的测试集只作回归。
9. 不伪造人工标注、试用结果或实验数字；模型标签不得表述为人工标签；没有做的如实写未完成。
10. 密钥不入库、不进日志、不出现在报告里。
11. 运行中的会话固定其场景、rubric 和规则版本；新版本只对新会话生效。
12. 每条数据记录都带标签等级、分区与来源；标注模型的输入只来自 `model_input`，不含 gold、路径夹具和探针预期。

| U7 | 实习部门的业务合成数据是否接入 | 暂不接入；格式上预留 `business_synth` 桶 | 需要授权和脱敏确认 |
| U8 | `data/external-samples/` 是否纳入版本库 | 纳入许可清楚的部分；许可不明的摘录只留在本地 | 目前整个 `data/` 未被跟踪 |
| U9 | 算力窗口 | 假定订阅在一周左右到期；代码密集的波次 0 到 2 在此之前完成 | 请给出确切日期 |
| U10 | 标注模型的接入方式 | 优先 API 密钥；没有则由 Agent 按批次文件执行 | 流水线两种方式都支持，见数据计划第 6 节 |
| U11 | 同伴试用人数 | 最少 3 人，目标 5 到 8 人 | 本期唯一保留在关键路径上的人工环节 |

已由用户裁定的事项（2026-10-06）：优先级可以调整（原 U2）；数据收集单独成计划；标注由模型完成，人工复核可选；不严格计算工作量；自带 Agent 与工程师路径的细节可由接手者补全。
