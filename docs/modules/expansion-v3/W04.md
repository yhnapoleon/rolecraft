# W04 三同事连续协作与资源协商

本模块把角色知识、调用者授权、生成输入、实际说出和展示回执分开。所有持久写入返回 W01 `Mutation`，异步生成经注册的 `v2.role_turn` handler 执行，资源生效经 `Mutation.decision` 与同一确定性策略复核。模块没有自建数据库事务、幂等、队列或租约。

## 安装契约

1. W02 从固定 hash 的场景包提供 `ScenarioKnowledge(binding, roles, materials, facts)`，绑定必须等于会话的 `SessionBindings.scenario`；角色和来源可以替换，不导入其他人的活动目录。
2. 在公共 `V2Store` 调用 `install_role_storage(store)` 注册本包 `role_turn`、`role_reply`、`role_display` 模型。
3. `create_role_service(store, catalog, model, event_reader=...)` 创建真正的 `ContextPort`；`service.install(registry)` 安装 `turns.create` 和 `v2.role_turn`。API/worker 使用同一冻结注册配置和本机数据库，依赖、凭据和进程仍各自独立。
4. `ScenarioApprovalPort.from_w02(package, evaluate)` 使用 W02 冻结的 approval_limits。`evaluate(request, view, auth)` 由 W02 的正式事务适配器把真实 TransactionView/不可变请求 basis 转给其确定性策略。不存在替代批准规则。还价候选也必须通过同一个 evaluate，超出场景、不足以支撑方案或已经不需要的档位不生成虚假 offer。
5. 安装 `NegotiationService.operation()` 至 `approvals.resolve`。公共集成人将 `service.actions(existing_w02_handler)` 和 `service.approval_policy(existing_w02_policy)` 接入原 actions 槽，只有 accept_counteroffer 分支由 W04处理。其余 W02 行为不覆盖。

## 角色上下文和记忆

`ContextPort.capture` 先检查 caller 凭据和发起动作，再通过公共 `role_reader` 读取该角色实际拥有的记忆。角色自己的材料不受 caller.allowed_objects 裁掉；针对该调用者的生成投影仍受权限限制。分享同时检查 caller 对 share/product 的读取权、接收角色、当前 share 修订、撤销状态和确切 product 版本。

静态材料 `observed_at_seq=0` 不足以激活版本，必须有真实 ScenarioState 的 `material_activation` 和 `source_versions` 相符。事件只包含已存事件的来源引用；不接受事件自由文本覆盖来源披露下限。never 不进入生成上下文，paraphrase_only 只取作者批准摘要，quote/span 从生成路径清除。prompt 使用 S 编号，不携内部 fact id。

回复以不可变 RoleReply 保存；同时固定实际 caller-safe prompt 及 hash，以便核对真实模型输入，公共回包只展示回复与安全投影。有来源的记忆来自该角色自己已保存的 question/reply，不把模型总结变成公司事实；经理自己已提交的审批决定以独立来源进入记忆，明确实际 granted 及初始资源之间的关系，其他角色不自动获知。已撤销分享不能重读，已说出的旧话继续按历史时点保留。模型失败沿公共 worker 的失败/重试状态恢复，不保存伪造回复，不产生资源变化。

生成时只对实际原句匹配的事实记录 SpokenEvidence；prompt 中的其余事实不会被记成已披露。模型自由转述没有独立语义核验时不升级为 verified。生成与 job 轮询都不意味着用户已展示；`record_reply_display` 需要客户端显式确认展示，才经 `project_disclosures` 输出 PublicDisclosureRecord。此记录也不代表理解。
