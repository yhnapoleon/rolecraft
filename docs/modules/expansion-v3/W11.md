# Scenario candidate construction and release boundaries

## Candidate CLI contract

This slice extends the authoring CLI with immutable candidate packaging. The existing
`validate --declaration <file>` contract is retained. New build/validation work starts
from a current-protocol scenario source directory and always stays outside the playable
catalogue. The interface below was fixed before implementation and is now available for candidates.

```sh
python -m career_lab.scenario_compiler build --source <scenario-dir> \
  --declaration <author-declaration.json> --output <fresh-candidate-dir> \
  --author-id <author-label> --revision <candidate-revision> \
  --evaluation-id <logical-id> --evaluation-revision <revision> \
  --evaluation-sha256 <root-file-sha256>
python -m career_lab.scenario_compiler validate --candidate <candidate-dir>
python -m career_lab.scenario_compiler publish --candidate <candidate-dir>
python -m career_lab.scenario_compiler attempts --root <dedicated-attempts-dir>
```

Build freezes only manifested package members and the exact author declaration. It
checks the Evaluation logical ID, revision and root SHA-256 supplied by the operator;
there is no embedded candidate rubric name or hash. The package remains eligible for
isolated standard-session verification, not public installation. Author labels identify
the generating attempt and confer no confirmation or review authority. Build/validate
return exit code 2 while trusted confirmation is missing, even when `package_status` is
`valid`. Consumers can inspect that explicit status and the frozen artifact; they must
not treat it as a publication result. The attempts summary returns 0 when readable.

Every started build has an audit record, including failed input/copy/validation attempts.
Failed attempts remain in the E8 denominator with generator `manual`; no model-generation
claim is made. Existing output directories and source packages cannot be overwritten. The `attempts`
command counts all direct subdirectories in a dedicated attempt root; interrupted or
unreadable records contribute an unresolved attempt instead of disappearing. Do not
place source packages or unrelated directories in that dedicated attempt root.

## Pending trusted release inputs

Publication cannot be completed with the current public interfaces. Missing inputs are
trusted declaration confirmation, installed business-effect semantics, an independent
content-review authority and verified business-terminal execution. A caller-supplied
reviewer name, file or digest cannot substitute for any of these.

The existing `scenarios/v2/release.py::original_review/read_release` trusts only the
installed historical review/continuity records. Its `require_evaluation` also pins a
single supported evaluation version. These are owned by the scenario integration line;
this compiler consumes them without changing or re-signing old packages. The minimum
follow-up is an authenticated, content-hash-bound confirmation/review reader and a
parameterized Evaluation identity accepted by the official loader.

BUILD-01/03/05/06 can be exercised for candidate packaging, current protocol validation,
exact content checks and attempt retention. BUILD-02's independent-review success and
BUILD-04's real terminal-path validation remain blocked at these public seams. A refused
publish command is not evidence that the full release chain works. No catalogue pointer
or `scenarios/pm_pilot/v2/installed/current.json` is changed by this line.
