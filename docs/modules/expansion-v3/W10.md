# Authorized full-history branching

The current branch has no full-history branching CLI. The existing public
`SnapshotPortAdapter` and `NamespaceRemapper` provide export/restore and typed identity
remapping; the earlier six-object consumer probe is not proof of the complete
FORK-01..06 workflow. No new branch, research export or authorization system is created
by this module documentation.

## Public assembly dependencies

The research line has implemented `research/authorization.py` at commit
`e0636707d7f6b1766a395d078d09a1c5c53c64ab`; it is not in this branch's imported main
baseline. The coordinator must integrate that owned module before this line can use
its `issue/validate/public_identity` interface with purpose `branch_restore`. A human
session credential alone is not research consent. The grant must cover the full
restored prefix, fixed session and all three logical-clock fields. Keys and bearer
grants must not enter public branch output or journals.

The remaining recovery seam is in `storage/v2_snapshot.py::SnapshotPortAdapter`.
It exposes restore but no read-only original-restore-result lookup. Calling restore
again re-enters the credential-issuance path; a missing reference credential can be
created after the underlying restore has already committed. Unknown outcomes therefore cannot be resolved by calling restore again.
The storage owner needs a narrow authorized read method (approximately 20–30 lines)
that accepts target session, original request ID and source snapshot hash, returns
the saved `RestoreResult` or a safe missing/conflict result, and performs no credential
issuance, writes, model calls or approval replay. The line estimate is provisional.
`read_snapshot/export/parent_digest` also create a research credential on a cold adapter
through `_research → research_context`; the owner must provide an authorized read path
that reuses established context without creating credentials during recovery. This line
will consume those methods; it will not query private tables or copy the restore
algorithm.

## Additional restore credential boundary

After integrating the credential-security update, an isolated current-core probe still
reproduces predictable child root credentials in `SnapshotService.restore()` (the
request-ID/no-explicit-token branch). It uses the parent token hash as an HMAC key,
combined with target session, request ID and source snapshot hash. The probe derived a
matching token without the deployment secret and successfully read the child through
the normal session API; no token or snapshot body is included in its report.

Storage/security ownership must migrate this branch to the shared secret-bound
derivation mechanism and verify repeat recovery/key-rotation behavior before full
branching is released. This is separate from read-only result lookup. The affected
derivation block is approximately 20 lines; a safe fix may require 20–40 lines plus
regression coverage because target identity and stored provenance must remain stable.
This line consumes the snapshot module read-only and has not patched it.
