# 前端接口需求与未实现功能

**日期：** 2026-10-05

**对应前端：** `apps/web` 工作台 v4

**读者：** 负责后端、场景和评价的同学，以及按本文实施的 Agent。动手前先读第 8 节。

**核对基线：** 2026-10-05 远端 `main` 为 `3a339bb`，后端代码自 `1ebd3a7` 起没有改动；文中的代码位置和行为按这个版本逐条复核过。

**本文回答三个问题：**
1. 前端需要后端提供哪些接口和字段。
2. 每个页面要呈现什么内容。
3. 哪些功能还没有实现。

现有接口的行为都核对过代码（文中给出仓库内文件位置），部分做了实际调用。新增接口只描述前端需要的输入、输出和验收方式，具体实现由后端决定。

---

## 先看这一段

现有后端共 16 个接口，新工作台用到其中 15 个。中英文界面都能完成一整轮：建会话、读资料、配置、测试助手、问同事、申请审批、交付、看评审。剩下的 relation-checks 是实验接口，新界面暂不提供入口。要让演示可信，并能用英文展示，后端最需要先解决下面六件事（P0）。

| # | 需要什么 | 为什么 |
|---|---|---|
| 1 | 会话级语言 `locale`（zh/en），并提供英文版场景材料、同事回复、助手回答和评审理由 | 当前所有内容只有中文；英文提问检索不到中文文档，会直接转人工。课程首轮按英文评测 |
| 2 | 同事回复要真正回答问题，并带上人物身份 | `local` 模式不看问题，只返回“本地事实模式：…（当前值：True）”这样的事实串 |
| 3 | 事件、回合、测试、成果、提交都带 `created_at`；回合带提问原文 | 现在没有任何时间戳。前端只能显示“这台浏览器看到它的时间” |
| 4 | 场景材料里删掉写给开发者和训练用的说明 | 例如“此材料仅用于虚构训练场景”“继续回答500元可能说明索引仍在使用v1”，后者等于直接给出答案 |
| 5 | 评审的证据要对应到具体条目，超长时不要整份降级 | 现在每个条目引用的证据完全相同；证据包超过 16,000 字节，所有条目都会变成“证据不足” |
| 6 | 确认“第 3 次操作触发政策更新”的计数口径 | 读资料和同事对话都计数。实测读一份资料、保存一次配置、做一次测试，政策就更新了 |

另外，工作台里的**同事提醒、排序建议和过程反馈**目前由前端按记录规则生成，界面上都标了“规则”或“规则示意”。它们用来呈现产品形态，后端接口到位后替换（P1-5、P1-8、P1-9）。

## 1. 前端现在是什么样

### 1.1 页面与路由

岗位选择（`#/`）→ AI 产品经理入口（`#/pm`）→ **工作板**（`#/work`）→ 事项工作台（`#/task/<id>`）、资料（`#/doc/<id>`）、测试台（`#/bench`）→ 上线评审（`#/review`）。

返回按层级走：工作板左上角是“离开”，其余页面是“工作板”。顶部面包屑显示当前所在的事项或资料。

### 1.2 工作板

接手工作后的主页，从上到下：

1. **委托与条件：** Priya 的原话；试点容量、可用开发、期望上线、索引最长滞后四个数。获批后显示新值和“原 30 人 · 已批准”。
2. **世界事件：** 例如“差旅政策更新为 v2”，说明索引是否落后；可以看哪里变了、记为事项或知道了。
3. **知识助手：** 配置版本、人数、知识范围、更新方式、政策与索引版本；测试台、设置、申请三个入口。
4. **事项看板：** 先做、随后、暂放三列，拖动或用键盘改优先级和顺序。卡片显示进展、标题、最新作品及用途、作品数、测试数、有提醒的同事头像，以及“测试早于政策更新”“N 份 Agent 回传待检查”。“问问怎么排”给出三位同事各自的排序。
5. **资料：** 标题、版本、未读、有新版本，以及“可以问”的同事（同样拿到这份资料的人）。

### 1.3 事项工作台

- **头部：** 优先级、标题、进展（待处理、正在做、已处理）、说明。在这件事里写下第一份作品、做第一次测试或带回 Agent 作品时，进展自动从待处理转为正在做；标为已处理由用户决定。
- **左侧目录：** 这件事的作品（用途、版本）、打开或引用过的资料、在这件事下做的测试（标出当时的政策版本）。
- **中间：** 当前对象。可能是直接可写的开始页、作品编辑器（用途、版本、保存状态、依据，旁边显示同事提醒）、一份资料（可与上一版对比）或测试台（结果记在这件事下）。
- **动作条：** 引用依据、测一测、问同事、交给我的 Agent、请求评审。

### 1.4 右栏

右栏有四个标签。在事项工作台里可以切换“这件事 / 整件工作”。

| 标签 | 内容 |
|---|---|
| 讨论 | 同事的提醒（标“规则”，可回应或先放下）；Priya、Mei、Daniel 和我的 Agent。和同事的对话里，每条你发出的消息标出所属事项和时间，可以附上作品或测试 |
| 反馈 | 请求评审后显示记录核对和观察：看到什么、当时可知什么、为什么重要、可以做什么；每条都可以写“我有不同看法” |
| Agent | 连接方式（任务包可用，MCP 未提供）；交出去（范围和数量）；带回来（粘贴或选文件，预览后进入事项，待你采用）；它做了什么；MCP 接入后的动作记录示例（标“示例”） |
| 动态 | 服务端事件、你的操作、同事回复、Agent 动作和同事提醒，按时间排列 |

### 1.5 颜色

每种颜色只表示一类意思：

| 颜色 | 意思 | 例子 |
|---|---|---|
| 黑 | 你和你能做的事；你的 Agent 用同一颜色 | 主按钮、你的消息、Agent 标志 |
| 琥珀 | 外面变了或已过期 | 政策更新、索引落后、测试早于政策更新、对比中新增的文字、被改变的条件 |
| 绿 | 站得住 | 已处理、已满足、已批准、可用 |
| 红 | 超出限制 | 试点人数超过容量 |
| 灰 | 还不知道 | 证据不足、需要核验 |

人物用固定色相区分：Priya 紫、Mei 洋红、Daniel 青、知识助手蓝。优先级用柱形（3、2、1 格），进展用圆形（空、半、勾）。“关于这个工作台”里有同样的说明。

### 1.6 语言

界面默认跟随系统语言，也可以在右上角手动切换。后端返回的中文内容（资料、同事回复、助手回答）在英文界面下原样显示，并标 “Chinese source”。`local` 模式的同事回复标“本地模式”，事实拆成列表显示。

### 1.7 数据来源

| 来自后端 | 只存在浏览器 |
|---|---|
| 会话与世界状态、资料（含 `visible_to`）、同事回复、试点配置、申请与审批、助手测试、交付稿、提交、评审、证据、过程记录 | 事项、优先级与进展；作品、版本和引用的依据；对话所属的事项；提问原文；同事提醒的搁置状态；采用排序建议的记录；过程反馈和“不同看法”；Agent 任务包导出、回传、采用与关联测试；各种“看到的时间” |

上表右列的数据只保存在浏览器，换浏览器会丢失，也不会进入评审。第 3 节 P1 列出了对应的接口需求。

## 2. 现有 16 个接口：前端怎样使用，发现了什么问题

### 2.1 使用情况

| 接口 | 前端用途 | 发现的问题 |
|---|---|---|
| `GET /health` | 判断是否连上后端 | `model` 取的是 serve 进程的 provider。实际执行同事回合的是 worker 进程，两者可能不一致 |
| `POST /sessions` | 接手一项工作 | 没有幂等键。也不能传入语言 |
| `GET /sessions/{id}` | 世界状态 | `logical_time` 只是事件计数，与 `version` 同步；没有时间戳；`material_versions` 里有 `tech_private`，学员能看到这份私有材料存在 |
| `GET …/materials?as_of_seq=` | 资料阅读；与旧版本对比；测试当时的来源；`visible_to` 用来显示“可以问”的同事 | 只能取源文档版本，取不回当时的索引内容 |
| `POST …/actions` | 阅读、试点设置、扩容和资源申请、刷新索引、暂停、恢复 | 每次阅读都计入政策触发次数（见 2.2） |
| `POST …/approvals/resolve` | “请 Priya 处理”申请 | 响应不含新状态；不批准时只返回英文 422，没有驳回记录；申请理由没有被任何环节读取 |
| `POST …/tests` | 测试台 | 返回整篇命中文档的原始 Markdown（以 `# 标题` 开头），其中包含给开发者的备注；只引用一篇文档；`indexed_versions` 的含义有歧义 |
| `POST …/turns` | 和同事对话 | 入队时不校验 `role_id` 和会话状态；不能附带事项、作品或测试；没有跨回合记忆；角色提示里没有人物姓名和职责；角色不知道政策已经更新 |
| `GET …/jobs/{id}` | 显示“正在输入”和评审生成进度 | 不返回任务类型和角色，前端只能从自己发出的请求推断 |
| `POST …/artifacts` | 保存交付稿（固定 6 个字段） | 一个会话只能有一份同结构的交付稿，没有多份作品、用途或依据引用 |
| `POST …/submissions` | 固定提交 | 提交即终态，不支持修订 |
| `POST …/feedback` | 生成评审 | 失败后同一提交无法重跑 |
| `GET …/feedback/{submission}` | 上线评审页的“上线检查” | 见 2.3 |
| `GET …/timeline` | 动态、过程记录、恢复提交编号 | 没有时间戳；回合不含提问原文；`record_turn` 对学员不可见，事件序号有空洞 |
| `GET …/evidence/{sub}/{criterion}/{eid}` | 查看评审依据 | 只能按条目取；没有可读摘要，前端按 `kind` 自行排版 |
| `POST …/relation-checks` | 新界面暂未使用；旧连接页 `/connected/` 保留入口 | 需要服务器配置冻结实验，本机未配置，返回 503 |

### 2.2 世界规则

- **政策更新的触发：**
  - 规则写在 `src/career_lab/scenarios/reducer.py:109-115`：第 3 次计数动作之后，政策自动升为 v2。
  - 除暂停和恢复外，所有动作都计数，包括读资料、测试、保存交付稿、同事回合和审批。
  - 实测：只和同事对话 3 次也会触发。
  - 前端已改为同一份资料的同一版本只发一次阅读请求。仍需要后端或场景负责人确认计数口径：是否只计入“影响试点判断的业务操作”（测试、配置、申请）。
- **审批条件：**
  - 写在 `src/career_lab/api/approvals.py:20-44`。
  - 要求先有配置，且配置里包含必要工作项和人工兜底，才可能批准。
  - 条件不满足时只返回英文错误，申请一直留在待处理状态。
  - 前端把这个错误翻成了“Priya 没有批准：当前设置不需要这项申请，或超出了可批范围”，但没有办法告诉用户具体缺什么。

### 2.3 评审（rules-v2）

- **证据完全相同：**
  - 写在 `src/career_lab/rubrics/checks.py:56`。
  - 每个条目的 `evidence_ids` 都是全部非文档证据（配置、交付稿、条件记录、所有测试），与条目无关。
  - 前端只好把它们合并成一行“评审读取的记录”。
- **超长整份降级：**
  - 写在 `src/career_lab/evidence/assembler.py:69-71`。
  - 每个条目的证据包都包含全部可读资料的全文、配置、交付稿和全部测试，`rationale` 还被计算两次。
  - 按 UTF-8 字节计超过 16,000 时，该条目降级为 `completeness: "overflow"`。各条目的内容几乎相同，所以会一起变成“证据不足”，证据清空，`practice` 为空。
  - 理由显示为“材料或日志不完整，暂不扣分”（`checks.py:18-19`），看不出是超长。
  - 实测下面两种情况都会触发：
    - 依据写到约 1,000–1,500 个汉字。
    - 做了 8 次 FAQ 测试。
  - 前端在交付面板里做了粗略估算和提醒，并让用户选择附上哪些作品，避免把全部笔记塞进依据。这只是缓解，问题仍在后端。
- **状态与理由：**
  - 按 `src/career_lab/rubrics/aggregate.py:25`，只要有条目需要复核就是 `pending_review`；而 `R2.support` 永远需要复核，所以现有规则下不会出现 `scored`。
  - `R3.resources` 的理由固定以“必要依赖已核验”结尾，依赖缺失、判为未满足时也是这样写（`checks.py:28`）。
  - `R4.functional_tests` 只统计提交时配置版本下的测试（`checks.py:30-32`）。之前在旧配置下做过的测试不计入，理由却写“完整日志中没有实际测试”，与事实不符。
  - `R4.staleness_test` 在政策更新后没有新测试时，理由写“开放动态政策但完整日志中没有实际测试”（`checks.py:41`）。更新前做过测试也是这句，与事实不符。

### 2.4 打断沉浸感的场景文字

以下文字出现在学员能读到的材料或助手回答里，建议移到不可见的场景备注中：

| 文件 | 文字 |
|---|---|
| `scenarios/*/v1/materials/policy-v1.md`、`policy-v2.md` | “模拟公司”“此材料仅用于虚构训练场景” |
| `policy-v2.md:5` | “源文档发布v2不代表知识助手索引已经更新。继续回答500元可能说明索引仍在使用v1，应记录测试所用版本。”（相当于直接给出答案） |
| `brief.md:5`、`brief.md:7` | “评价不强制要求询问某个角色”“测试功能由后续模块提供” |
| `business.md:7` | “本模拟不提供真实企业ROI预测” |
| `approval-process.md` | 直接写出 `capacity_approved`、`resources_approved` 等事件 ID |
| `runtime/loop.py:31` | 同事提示词“你是模拟公司的同事” |
| `runtime/model_adapter.py:48` | 同事回复以“本地事实模式：”开头，并带“（当前值：True）” |

## 3. 需要新增或调整的接口

优先级的含义：
- **P0**：英文展示和可信演示必需。
- **P1**：项目定义 10/4 已确认的产品能力，目前只在前端本地实现，或由前端规则代替。
- **P2**：后续能力。

下面的字段名是建议；只要语义一致，前端可以跟着后端调整。

### P0-1 语言

- **建会话：** `POST /sessions` 增加 `locale: "zh" | "en"`。会话语言创建后固定，保证同事、助手、评审和证据使用同一语言。
- **影响范围：** 返回给学员的所有文字都按会话语言生成，包括：
  - 资料标题和正文、同事回复、助手回答和转人工文案；
  - 评审 `reason` 和 `practice`、审批理由、错误信息。
- **检索：** 英文会话的检索和同事上下文使用英文材料。
- **错误：** 在现有的 `error` 字符串之外增加稳定的 `code`，例如 `{"error": "...", "code": "approval_not_needed_or_over_limit"}`，前端按错误码显示本地语言。`error` 原文先保留，前端目前靠它翻译。
- **验收：** 用 `locale: "en"` 建会话后，问 “What is the hotel limit?” 能检索到差旅政策；资料、回复和评审都是英文。

### P0-2 同事与人物

- **人物信息：** 会话状态或 `GET /sessions/{id}` 返回 `roles: [{id, display_name, title, knows}]`。前端目前写死为 Priya、Mei、Daniel。由后端提供后，提示词、回复和界面能保持一致。
- **回复质量：**
  - 演示环境的 worker 使用真实模型（`--provider deepseek|openai`）；
  - 或者改进 `local` 模式，让它针对问题、按角色可见事实组织回答。
  - 两种方式都不应出现“本地事实模式”前缀或 `True` 这类原始值。前端现在识别这个前缀，标“本地模式”，只是临时处理。
- **角色上下文：** 角色能得知已发生、且对它可见的世界事件，例如政策已更新、某项申请已批准。
- **验收：**
  - 问 Priya “我应该先弄清什么”，回复是针对这个问题的一段话。
  - 政策更新后问 Mei，她知道政策变了。

### P0-3 时间与提问原文

- **时间戳：** 以下记录都带 `created_at`（ISO 8601，UTC）：
  - `timeline.events[]`、`timeline.turns[]`；
  - 测试结果、交付稿、提交；
  - 任务 `jobs`，并增加 `queued_at`、`started_at`、`finished_at`。
- **提问原文：** `timeline.turns[]` 增加 `question`。
- **任务信息：** `GET …/jobs/{id}` 增加 `kind`（`turn` / `feedback`）和 `role_id`。
- **用途：**
  - 对话和动态显示真实时间；
  - 换设备时对话完整；
  - 显示“Priya 正在输入”时不依赖浏览器缓存。

### P0-4 场景材料清理

- **材料：** 按 2.4 处理。
- **助手回答：** 改为返回命中的段落和引用位置，不返回整篇文档原文，例如 `answer` 加 `citations[].span`。
- **验收：** 任何学员可见文本都不出现“模拟”“虚构训练”“事件 ID”和答案提示。

### P0-5 评审证据与超长处理

- **证据对应条目：** `items[].evidence_ids` 只列与该条目有关的证据。
- **证据摘要：** `sources` 或 evidence 接口返回可读的 `summary`，例如“测试：住宿报销上限是多少？（配置 v2）”。
- **超长处理：** 不再整份静默降级。可选做法：
  - 提高上限；
  - 按来源截断并标记 `truncated: true`；
  - 把证据包内部已有的 `completeness: "overflow"` 透出到反馈结果，并给出超出量。
- **修正理由：** 修正 2.3 中与事实不符的三条理由（`R3.resources`、`R4.functional_tests`、`R4.staleness_test`），超长时不再写“材料或日志不完整”。
- **验收：** 依据写到 3,000 字、做 10 次测试，评审仍能给出逐条结论，或明确说明哪部分被截断。

### P0-6 政策触发口径

- **需要确认：** 触发规则计入哪些动作，或改为以“测试次数”“配置次数”触发。
- **前端现状：** 同一版本的资料只发一次阅读请求。
- **需要说明：** 后端如果保留“读资料计数”，请说明重复阅读是否计数。

### P1-1 事项（任务卡）

```
GET    /sessions/{id}/tasks
POST   /sessions/{id}/tasks            {title, note, priority, origin, parent_task_id?, request_id}
PATCH  /sessions/{id}/tasks/{task_id}  {title?, note?, priority?, status?, position?, expected_version}
```

- **字段：** `id, title, note, priority (first|next|later), status (open|working|done), position, origin (seed|user|situation), parent_task_id, created_at, updated_at`。
- **事件：** 新建、改优先级、改顺序、改进展、拆分都写入时间线。前端会在用户开始写作品、做测试或带回 Agent 作品时，把进展从 `open` 改为 `working`；后端只需记录这次修改。
- **用途：** 评审能看到用户怎样安排工作；同事回答优先级问题时知道有哪些事项；换设备不丢。

### P1-2 作品（多份、带用途和版本）

```
GET    /sessions/{id}/works
POST   /sessions/{id}/works                    {task_id, title, purpose, body, source, request_id}
POST   /sessions/{id}/works/{work_id}/versions  {title?, purpose?, body?, evidence[], expected_version}
POST   /sessions/{id}/works/{work_id}/adopt     {request_id}
```

- **`purpose`：** `explore | option | plan | commit | free`，界面上分别是探索笔记、方案比较、测试计划、试点决定、自由作品。
- **`evidence`：** 列出引用，例如 `[{type: material|test, id, version}]`。
- **`source`：** `user | agent`。
- **用途：** Judge 需要知道作品的用途和版本，才能区分“探索中的假设”和“正式承诺”（项目定义：情境化评价）。

### P1-3 交付不限于固定 6 个字段

- **提交内容：** 提交时可附 `work_ids[]`。另提供九项业务责任作为可选结构化字段：用户范围、知识范围、容量、更新方式、兜底、工作项、验收测试、成功指标、退出条件。
- **兼容：** 现有 6 字段继续兼容。
- **长度上限：** 写入接口返回明确的长度上限，前端据此提示。

### P1-4 交付后修订

- **接口：** `POST /submissions` 支持 `parent_submission_id`，形成关联版本。
- **会话状态：** 会话不再在首次提交后终止，或增加 `revising` 状态。
- **评审：** 每次提交都有自己的评审，可对比前后两次。

### P1-5 同事主动发言与记忆

- **记忆：** 角色回合带上与该角色的历史对话。
- **主动发言：** 场景事件或用户的作品可以触发角色主动发一条消息。消息出现在 `timeline.turns`，带 `initiated_by: "role"`、`trigger`，以及相关的 `task_id`、`work_id`。
- **前端现状：** 下面六条规则生成提醒，标“规则”。用户可以回应（打开与这位同事的对话），也可以先放下。

  | 同事 | 触发条件 |
  |---|---|
  | Priya | 试点决定里写的人数超过当前容量 |
  | Priya | “先做”列有 3 件或以上事项 |
  | Mei | 试点决定正文超过 120 字，但没读业务范围，也没和 Mei 谈过 |
  | Mei | 政策更新之后 |
  | Daniel | 有测试引用了已经过期的版本 |
  | Daniel | 采用了 Agent 带回的作品，但没有关联任何测试 |

- **前端呈现：** 讨论栏的“同事的提醒”、作品旁注、事项卡和团队头像上的标记、动态。后端消息接入后用同样的位置显示，去掉“规则”标记。
- **验收：** 政策更新后，Mei 主动来一条消息，内容与当前事项相关；用户回复后她记得自己说过什么。

### P1-6 申请与审批记录

- **申请：** `pending_requests` 改为对象：`{id, kind, reason, status (pending|approved|denied), created_at, decided_at, decision_reason}`。
- **不批准：** 写入 `approval_denied` 事件，`decision_reason` 用会话语言说明缺什么。
- **审批响应：** `POST approvals/resolve` 返回新状态。

### P1-7 读取与列表

- **列表接口：** `GET …/tests`、`GET …/artifacts`、`GET …/submissions`。
- **用途：** 刷新或换设备后能还原测试记录和交付历史。现在这些只存在浏览器里。

### P1-8 排序建议

```
GET /sessions/{id}/advice?role_id=supervisor|business_lead|tech_lead
→ {role_id, items: [{task_id, priority}], why, based_on: [{type, id}]}
```

- **依据：** 当前全部事项（包括用户自己加的）、该角色可见的资料和世界状态。
- **不自动应用：** 用户选择“按此排列”后，前端调用 P1-1 的 `PATCH`，并记录采用了谁的建议。
- **前端现状：** 每位同事一条固定顺序，只覆盖三件起始事项：Priya 是决定、需求、政策；Mei 是需求、政策、决定；Daniel 是政策、需求、决定。界面标“规则示意”，按此排列后可以撤销。
- **验收：** 用户新加一件事后，建议能覆盖它；政策更新后，Daniel 的理由提到这次变化。

### P1-9 过程反馈（请求评审）与不同看法

```
POST /sessions/{id}/reviews                          {work_id?, task_id?, request_id}  → {job_id}
GET  /sessions/{id}/reviews/{review_id}
     → {checks: [{ok, text}],
        observations: [{id, tone: good|check|unknown, title, observed, basis, why,
                        actions: [{kind, target_id}], refs: [{type, id}]}]}
POST /sessions/{id}/reviews/{review_id}/disputes     {observation_id, text, request_id}
```

- **`basis`（当时可知）：** 只能使用那个时刻用户看得到的事实，不能用事后才出现的信息。
- **定位：** 不打分，不替代正式评审；不同看法写入时间线，正式评审可以读到。
- **前端现状：** 规则写在 `apps/web/src/app/coach.js`，标“规则示意”。
  - 记录核对：作品已保存的版本；试点人数与容量；工作项成本与可用人日；测试次数和最近一次的配置版本；最近一次测试之后配置或政策是否变过。
  - 观察：发现旧答案后是否收住了风险；有回答用了旧版本；政策更新后还没重测；决定里的人数超过容量；决定缺少需求方面的依据；还没有试点决定；Agent 作品没有关联测试；用户自己加的事项下面有产出；资源获批后是否真的改了配置。
  - “我有不同看法”只存本机。
- **验收：** 政策更新前做的测试，反馈说明“当时结果没有问题”；更新后提示重测；对同一条观察提出的不同看法，刷新后仍在。

### P1-10 对话上下文

- **请求：** `POST …/turns` 增加 `task_id?`、`work_id?`、`attachments: [{type: work|test, id, version}]`。
- **返回：** `timeline.turns[]` 带回这些字段。
- **用途：** 讨论可以按事项筛选；同事回答时知道你在做哪件事；评审能看到求助发生在哪件事上。
- **前端现状：** 浏览器记录每条消息属于哪件事；附上的作品或测试作为消息正文发送。

### P1-11 外部 Agent（接入方式与排期待定）

项目定义把自带 Agent 定为通用协作入口：MCP 与任务包导入都是候选方式；连接不自动启动外部 Agent，也不同步全部文件；回传、采用、执行和验证要分别显示，用户能看到 Agent 做了什么、改了什么、结果如何。

- **前端现状：**
  - 任务包：用户勾选范围（这件事或整件工作；作品、读过的资料、测试记录），复制或下载。任务包里有范围、请求编号和回传格式，不含会话凭据。
  - 带回：粘贴 Markdown 或 JSON、或选文件，预览后放进事项，状态是“待检查”；用户采用后才算接受。
  - “它做了什么”：记录交出、带回、采用、关联测试。
  - MCP 的动作记录只显示示例，标“示例”。
- **任务包方式需要的接口：**

  ```
  POST /sessions/{id}/agent/packages  {scope: {task_id?, work_ids[], material_ids[], test_ids[]}, request_id}
       → {package_id, content}
  POST /sessions/{id}/agent/returns   {package_id, content, request_id}
       → {work_id, status: "to_check"}
  ```

  - 回传按 `request_id` 幂等。
  - 采用、关联测试写入时间线。
- **MCP 方式需要的能力（如采用）：**
  - 按会话发放、只覆盖用户所选范围的凭据，可随时撤销。
  - 只读工具：列事项、读资料（仅用户可见的）、读作品、读测试记录。
  - 提议工具：新建作品草稿（落为“待检查”）、请求运行测试（用户确认后才执行）。
  - 每次调用写入时间线：`{actor: "agent", tool, summary, result_summary, created_at}`。
  - `GET /sessions/{id}/agent/log`，供“它做了什么”显示。
  - 具体工具清单由后端和产品一起确认。
- **不做：** 托管用户的 Agent 账号；未经用户确认就执行写操作。

## 6. 通用约定（建议）

- **鉴权：** 会话凭据继续用 `Authorization: Bearer`。凭据只存在浏览器，前端不会写进任务包或导出文件。
- **写入幂等：** 所有写接口都带 `request_id`，重放返回原结果。目前 `POST /sessions` 是例外，建议补上。
- **版本：** 改世界状态的写入带 `expected_version`；冲突返回 409 和当前状态。
- **错误：** 在现有 `{"error": "..."}` 上增加 `code`；会话语言（P0-1）到位后，`error` 按会话语言生成。
- **时间：** 一律 ISO 8601 UTC。前端按用户语言格式化。
- **文本：** 学员可见正文使用 Markdown 子集：标题、列表、粗体、行内代码。不要输出 HTML。
- **长度：** 每个写入字段在接口文档中写明上限，超限时返回错误码，不要静默截断。
- **状态类别：** 新增的状态字段请说明属于哪一类（外部变化或已过期、站得住、超出限制、还不知道），前端按 1.5 的颜色显示。

## 7. 怎样联调与验收

- **启动：** 前端主入口 `apps/web`，启动方式见 [apps/web/README.md](../../apps/web/README.md)。
- **自动检查：** 每次接口变更后，前端会跑：
  - `npm test`，含真实 HTTP 集成测试：`ROLECRAFT_TEST_API=http://127.0.0.1:8510/api npm test`；
  - 浏览器走查：中文、英文、手机宽度、深色模式、按系统语言自动选择；另走一轮申请审批、Agent 带回与采用、新建事项。
- **请后端在合并前说明：**
  - 新字段是否向后兼容；
  - 旧会话是否仍能读取；
  - `locale` 和时间戳从哪个版本开始提供。
- **前端跟进：** 第 3 节每完成一项，前端去掉对应的本地替代逻辑或“规则”标记，并在第 5 节标记完成。
